# 飞书助理（Feishu Assistant）

**项目群助理**：把机器人拉进一个项目群，@ 一下用一句自然语言把事办掉 ——
在本群立项目（可以改名）、往项目日志里记一条、按时间范围复盘、
把本群的聊天记录总结进日志、派任务给同事（进甘特图），
以及改动它自己建过的那些任务（标记完成、改起止、改状态、加协作人）。

> **项目日记**（在群里记项目日志、派任务/甘特图、按时间范围复盘、总结群聊，
> 数据同步到多维表格）是本模块的主用途，用法和设计单独成文：
> [FEISHU_DIARY.md](./FEISHU_DIARY.md)。

### 范围：这是项目群助理，不是通用飞书机器人

曾经还有五个动作：建/改/删日程、查忙闲、给同事发私聊消息。**已经整套删掉**，
理由不是"用得少"，而是留着它们要付两笔代价：

1. **动作清单原样进 prompt**，每多一个语义相邻的动作就多一处误选面。
   「给张三派个任务，明天开始」在有 `create_calendar_event` 的年代会被拆成
   建任务 + 建日程两步，而用户只想要一条任务。
2. **它们独有的权限点**（`calendar:calendar.event:create/update/delete`、
   `calendar:calendar.free_busy:read`）是接入时最容易卡住的几项。
   让用户为用不到的功能去开一批权限，是把绑定流程里最容易失败的一步无谓地加长。

要日程和私聊消息的话，飞书自己的机器人和日历就是干这个的，不必由本助理代劳。
下面提到「写操作」时，指的就是建项目 / 改项目名 / 记日志 / 总结群聊 /
建任务 / 改任务这几件事。

同一笔账也决定了 `im:message.group_msg`（读群里没 @ 我的消息，「总结群聊」用）
**不进必需权限清单**：它是飞书审得最严的一档，而那个功能不是所有人都用。
它走 `optionalScopeGroups()`，在接入指引里单独列一段「用到 XX 时再开」——
代价是第一次用会失败，但失败信息是翻译过的「缺哪个权限 + 一键申请链接」。
删动作和降级权限是同一条原则的两半：**接入流程里最容易失败的那一步，
不为少数人用的功能加长**。

这是平台上**第一个入向（inbound）**的飞书集成。已有的 `services/tender/feishuNotify.ts`
和 `feishuBitable.ts` 都是出向的（我们主动推数据过去），本模块反过来：飞书把事件推给我们。

## 一、整体链路

```
用户在飞书里 @ 机器人「记一下：客户要把 logo 改大」
        ↓  （飞书 websocket 长连接，我们主动连出去）
connection.ts   LarkChannel 收到 message 事件，剥掉 @ 占位符、归一化 mentions
        ↓
dispatcher.ts   只收群聊 → 群白名单 → message_id 去重 → 落一条 pending 日志 → 立刻返回（<3s）
        ↓  （游离 promise，不阻塞飞书）
dispatcher.ts   贴一个「收到了」表情 → 过并发闸排队（concurrency.ts）
        ↓
intent.ts       调 LLM（strong 档 + json_object）→ { steps: [{action, params}, …] }
        ↓
actions/*.ts    逐步调飞书 OpenAPI 干活（部分成功要说成部分成功，见第七·二节）
        ↓
dispatcher.ts   落终态日志 → 回帖告知用户结果
```

链路上**通常只有一次 LLM 调用**（意图解析，`strong` 档 + `json_object`）。
两个动作会再花一次（`fast` 档，归纳成文）：`review_diary` 复盘、
`digest_chat` 总结群聊 —— 所以它们一条指令记两次额度，
而且第二次只在那段范围里**真有内容**时才花（见 FEISHU_DIARY 第七节）。

## 二、为什么是长连接而不是 webhook

用户其实有公网 HTTPS 域名，仍然选长连接，因为它把下面这些整块砍掉了：

| webhook 要做的 | 长连接 |
|---|---|
| 维护一个公网回调地址，改域名要回飞书后台改 | 不需要地址 |
| 处理 URL 验证挑战（`challenge` 握手） | 不存在 |
| 验签（`X-Lark-Signature`） | 不需要 —— 连接本身已鉴权 |
| Encrypt Key 的 AES 解密 | 不需要 |
| 对外暴露一个 public 路由（新增攻击面） | **本模块零 public 路由** |

代价与前提：

- 仅**自建应用**可用（商店应用不支持）。本模块本来就只服务自建应用。
- 单应用最多 50 条连接。
- 只能收**事件**，收不到**回调**（卡片按钮点击属于回调）。这也是"完成后回帖告知"
  而不是"发个确认卡片让用户点"的原因之一 —— 好在用户明确说了不需要确认步骤。
- **必须单实例部署**。长连接是竞争消费：同一事件只投给其中一个实例，
  多实例下每个实例都会连上，谁收到不确定。本项目已经是单实例
  （`core/jobs.ts` 的 `reapZombieJobs()` 开机把所有 running 任务判失败，
  这个做法本身就以单实例为前提），所以不构成新约束。

## 三、3 秒限制怎么绕

飞书要求 3 秒内处理完事件，超时或抛异常都算失败，然后按
**15s / 5min / 1hr / 6hr** 重推，最多 4 次。而理解一句话必须调 LLM，必然超 3 秒。

`dispatcher.handleMessage()` 的同步部分只做三件廉价的事，然后立刻返回：

```ts
if (群聊 && 不在白名单) { recordRejected(...); return 'not_allowed'; }
if (!claimEvent(messageId, ...)) return 'duplicate';   // 去重
const commandId = startCommand({...});                  // 落 pending 日志
void execute(commandId, msg, deps);                     // 故意不 await
return 'accepted';
```

因此 `execute()` 是一个**游离的 promise**，抛出去只会变成 `unhandledRejection`。
它内部必须自己 catch 到底，且无论成败都要：落一条终态日志 + 回一句话。
失败时把**错误原文**回给用户 —— 缺权限、时间说不清这类问题用户能自己解决，
兜成"出错了"就永远卡住（他看不到服务端日志）。

### 「收到了」的表情贴在排队之前

`execute()` 第一件事是给原消息贴一个 `OnIt` 表情（`deps.ack`）。真活要等 LLM，
群里那几秒完全没有反馈，而这个模块最常被报的问题就是"@ 了没反应"——
分不清"在办"和"没收到"的人会再 @ 一遍。

两个位置上的讲究：

- **在并发闸之前贴**。忙时排队本身就是最需要反馈的那十几秒，贴在闸后面
  等于恰好在最需要它的时候不贴。
- **失败完全忽略**。`im:message.reaction` 不在必需权限里（少开它是常态），
  为一个装饰性的表情让整条指令失败是荒唐的。

### 没有任何东西在限制并发，所以要有一个闸

`void execute(...)` 意味着**同时有多少条指令在跑是不受控的**：一个部门早上九点
集体 @ 一下，就是同时几十个 LLM 请求打向同一把 key；多租户下每家公司各一条
长连接，它们还共用平台那把 key。撞限流的后果不是"慢一点"，而是用户拿到一段
英文报错，而他做的事完全正常。

`concurrency.ts` 的 `withIntentSlot()` 因此包住**意图解析这一段**：
`MAX_CONCURRENT = 4` 并发，`MAX_QUEUED = 20` 排队，队伍满了抛 `TooBusyError`
（回一句「过十几秒再说一遍」）。

- **闸只包意图解析，不包整个 `execute`**。`TooBusyError` 的文案承诺
  「本次没有执行任何操作，重说不会重复」——这句话的正确性完全靠这个位置：
  此时一个写操作都还没发生。挪到包住 `execute` 就会变成一句谎话
  （被拒绝的指令可能已经发出去半条消息了）。
- **排队也要有上限**。无上限排队把"限流"换成"永远不回"：排到几百条时最后
  那个人等到的是十分钟后的回帖，而他早当助理坏了、重发了三遍。
- **闸不在 gateway**。gateway 是全平台共用的（写作台、诊断都走它），
  在那里限流会让一个飞书群的早会通知拖慢正在网页上等结果的人。

### LLM 挂死时必须自己超时

OpenAI SDK 的默认值是**10 分钟超时且超时会重试**，最坏一次 `create()` 能挂
将近半小时。在别的路径上那只是"慢"，在这里是**指令日志永久停在 `running`、
群里一句回帖都没有**——`execute` 是游离 promise，没有任何东西会来叫醒它。
`core/llm/gateway.ts` 把 `DEFAULT_TIMEOUT_MS = 120_000` 和 `maxRetries = 1`
一起收紧（只设 timeout 的话最坏耗时仍是它的 2 倍）。

## 四、去重：认 message_id，不认 event_id

飞书的事件投递是 **at-least-once —— 成功也会重推**。不去重的话，
"帮我建个任务"会建出两个任务。

- 去重键是 **`message_id`**，不是 `event_id`（同一条消息的多次投递 `event_id` 可能不同）。
- 落库去重是权威的（`feishu_events` 表，`message_id` 作主键）。用 INSERT 的
  主键冲突判断，而不是先 SELECT 再 INSERT —— 后者在同一条消息被并发投递两次时
  会双双通过检查。
- LarkChannel 自带的 `safety.dedup` 是**内存**去重，进程重启就失效，
  而飞书会重推到 6 小时后。所以它只当免费的前置过滤。
- 第二道防线是各动作的幂等键：任务 `client_token`、消息 `uuid`。
  即使去重被绕过（比如库刚被清），也不会建出两份。
- `feishu_events` 每条 @ 消息一行，会无限增长。`cleanupOldEvents()` 删 7 天前的行
  （远超飞书 6 小时的重推窗口）。它**挂在 `logCleanupService` 每天 02:00 的 cron 上，
  不是启动时清一次**——这个服务是单实例长连接、正常几个月不重启，
  "启动时清理"实际等于"永不清理"。指令日志同理（`cleanupOldCommands`，14 天，
  和 `ai_logs` 同一个保留期）。

### 攒批必须关掉（`safety.batch.text.delayMs = 0`）

LarkChannel 默认把**同一个会话**里 600ms 内到达的消息攒成一批，`mergeBatch()` 用
`\n\n` 把正文拼起来、元数据取**最后一条**的。这个默认值是为聊天机器人设计的
（一个人分三行打完一句话，攒起来理解更好），但助理收的是**指令**：

同一个群里两个人几乎同时 @ 机器人（早会上一人记日志、一人派任务，不罕见）时——

- 两条正文被拼成一条，LLM 当成一句话解析；
- messageId 只剩后一条的 → 前一条**从来没被 `claimEvent` 登记过**，指令日志里彻底没有它；
- 回帖 `replyTo` 也是后一条，前一个人连"我的指令去哪了"都无从追问。

也就是一个人的指令**静默消失**，正是本模块从头到尾在防的失败模式。
`delayMs: 0` 命中 `ChatPipeline.push()` 的短路分支（不启攒批定时器），
但**保留每个 chatId 的串行链**——同群消息仍按序进 dispatcher，只是不再合并。

## 五、身份模型：为什么机器人是"另一个普通用户"

这是本模块最反直觉的一点。我们只用 `tenant_access_token`（应用身份），
不做用户 OAuth（SDK 不托管 user token，要自己实现授权 + refresh，且每个用户都得授权一次）。

在**任务**系统的视角下，`tenant_access_token` 没有任何特权，就是另一个普通用户。于是：

- **建任务**：机器人以自己身份创建，把真人用 open_id 加成
  `members: [{id, type:'user', role:'assignee'}]`（`create` 时内联传即可，
  不用再调 `add_members`）。任务随即出现在此人任务中心的「我负责的」里。
  代价：创建者显示为机器人。
- **查任务做不到**。应用只能看到自己创建的任务，「查我的任务」需要 user token。
  所以本模块**没有读任务的动作**，只能建。这也决定了改任务时「找不到」的话术，
  见第八·三节。
- **多维表格**（项目日记那三张表）也是机器人建的、机器人拥有的。
  连带后果有两个，都在 [FEISHU_DIARY.md](./FEISHU_DIARY.md) 里：
  表**不在任何人的云文档空间里**（所以链接是唯一入口，所以需要
  `list_diary_projects` 这个"问回来"的动作），以及表要**主动授权给群**
  （只读）并**主动关掉链接分享** —— 后者不关就跟随租户默认值，
  而默认往往是「组织内获得链接的人可阅读」，而链接是发在群里的。

### 为什么不做用户 OAuth

`user_access_token` 能让机器人以本人身份干活（任务的创建者是本人、
多维表格归本人所有），但拿到它只有 OAuth 授权码流程一条路，代价是：
一个**公网 HTTPS 回调路由**（本模块现在零 public 路由，见第二节）、
每人各自在浏览器里授权一次（现在飞书里说话的人**不需要平台账号**）、
存 + 刷新一对会过期的 token（`access_token` 约 2 小时）。
而且 `refresh_token` 到期后是**静默失效**：用户在设置好几周之后开始用不了，
早忘了自己授权过什么 —— 现有机制里没有这类"配好了又坏掉"的状态。

而"创建者显示为机器人"这件事，用户已确认接受。顺带一提：OAuth
**也绕不过 230013**（可用范围），因为授权本身就要求人在可用范围内。

## 六、open_id 从哪来：两个来源，都不经过模型

「给张三派个任务」里的"张三"要变成 `ou_xxx` 才能调接口。

这一节的**唯一不变式**：`open_id` 绝不能由 LLM 产生。它确实会编 `ou_xxx`，
而把消息发给错误的人是本模块从一开始就划定的不可接受的失败模式。

按名字查人的接口（`search/v1/user`）**只能用 user_access_token**，所以不能在
执行路径上现查。于是 open_id 只有两个来源，都在代码里，模型碰不到：

| 来源 | 需要的权限 | 什么时候用 |
|---|---|---|
| 事件的 `mentions[]` | 无（`name` + `open_id` 一起送来） | 群里 @ 过对方，最准 |
| 本地名册 `feishu_directory_users`（057） | 通讯录读权限，或降级用 `im:chat:readonly` | 没 @ 的人（包括不在本群的人） |

### LLM 只输出姓名

`intent.ts` 的 prompt 里**一个 open_id 都没有**（mentions 只列 `name`）。
以前是「姓名 → open_id」对照表 + 事后校验；现在模型看不到 id 就编不出来，
这比事后校验更彻底。`intent.test.ts` 有一条反向断言守着：整段 prompt 里
不许出现 `/ou_[a-z0-9]{4,}/`。

动作参数收的也是姓名：`create_task.assignee`、`update_task.followers`（姓名数组）。
老参数名 `assignee_open_id` 仍被读取，只是会落到 `resolvePerson` 的 `ou_` 拦截分支。

### 名册让「不在本群的人」也能被指名

`actions/people.ts` 的 `resolvePerson(who, ctx)` 是唯一的解析入口，优先级：

1. `ctx.mentions` 按 open_id 匹配（兼容 LLM 仍给 id 的情况）
2. `ctx.mentions` 按姓名匹配（**优先于名册** —— 名册是快照，可能过期）
3. 姓名以 `ou_` 开头 → 直接判定为编造，抛错
4. `findByName(appId, who)` 查名册（**归一化后精确相等**）

失败的三种情况**必须分开说**，且都以「你 @ 一下对方」作为百分百可靠的退路：

| 情况 | 话术 | 为什么不能含糊 |
|---|---|---|
| 查不到 | 「通讯录里没有找到「X」…如果还没同步过组织架构…」 | 含糊成「找不到」会让用户以为是同步没做，反复重试 |
| 同名多个 | 把各人的部门/职位列出来让他重说 | **绝不挑一个**。挑错人是静默的错误结果 |
| 已离职 | 「「X」已标记为离职」 | 同上，会被误当成同步没做 |

`findByName` **刻意不做模糊/前缀匹配**。「张」命中多个时挑一个是错的，
而真正的坏情况是公司里只有一个人姓张 —— 它会默默把消息发给一个用户
根本没想过的人。要模糊搜索请用后台的名册页，那里由人来选。

`createTask` 解析失败时**抛错，不回落到发言人**：用户说「给李四建个任务」
而任务落在他自己头上，是一个看起来成功了的错误结果，他要过几天才会发现
李四根本不知道这件事。`updateTask` 同理，把姓名解析放在**所有写操作之前**
（见第八·三节）—— 反过来的话用户会得到「截止时间改好了，但张三没加上」，
而他重下指令又会把截止时间再改一遍。

### 名册怎么来（`directory/sync.ts`）

绑定应用成功后**自动同步一次**（不 await，几十秒），之后可以在
「组织架构」页手动重新同步。两条路：

- **主路 `contact/v3`** —— BFS 遍历部门树（含根部门 `'0'`，直属公司根的高管
  不在任何子部门里），逐部门 `user.findByDepartment`，按 open_id 去重、
  跨部门的人合并部门名。拿到全公司 + 部门归属。
- **兜底路 `im/v1`** —— `chat.list` → `chatMembers.get`，只要 `im:chat:readonly`，
  **零通讯录权限**。只覆盖机器人所在的群、没有部门信息（同名时退化成「请 @ 一下」）。

**只有「通讯录注定读不到」才降级**（`isContactUnavailable`，判 code 不判文本）。
有三种，都是同一个后果，所以走同一条兜底路：

| 情况 | 飞书给的 | 用户要去哪 |
|---|---|---|
| 权限**点**没开 | code `99991672` | 权限管理 > **API 权限** |
| 权限点开了、通讯录**范围**是空的 | code `40004`，msg 只有 `no dept authority error` | 权限管理 > **数据权限 > 通讯录范围** |
| 范围里没勾任何部门 | **不报错**，接口全 200 但返回 0 人 | 同上 |

后两种是同一件事的两种表现，都必须单独翻译：`no dept authority error` 照抄给用户
等于没说，而他看到权限点全是绿的会开始怀疑我们的代码。第三种更隐蔽 —— 飞书认为
「你能读的范围内确实没人」不算错误，所以只能自己判 `list.length === 0`
（`ContactEmptyError`）。不判的话它会走进整批替换，把上一次的好名册清成 0 人
并显示「已同步」。

网络/限流/5xx **不降级**：那会掩盖真实原因，让用户拿着一份不完整的名册以为成功了。
**两条路都拿不到人时算失败**，同样不写空名册（管理员收回权限 + 机器人还没进群
的组合会让一份好名册变成零人）。

实际走的是哪条路记在 `feishu_apps.dir_source`，兜底路的 `note` 会原样显示在前端 ——
里面既说覆盖面（只有机器人在的群、没有部门），也带上真实原因和补救步骤，
否则用户知道「降级了」但不知道下一步做什么。前端的 `.dir-note` / `.conn-error`
都是 `white-space: pre-wrap`：这段话是分行写的，挤成一坨就没人看了。

**同步失败不清空已有名册**：一次网络抖动不该让助理突然不认识任何人。
成功时是「先删后插」的整批替换（一个事务），这样离职并从通讯录移除的人
才会从名册里消失 —— 留着他只会让助理一直把任务派到一个失效的 open_id 上。

`intent.ts` 的 `directoryHint(peopleCount)` 把「有没有名册」这个**运行时事实**
告诉 LLM（`dispatcher` 每条指令查一次 `countUsers`）：没名册时提到没 @ 的人
应该用 `reply` 请他 @ 一下；有名册时才该直接选写操作并填姓名。

## 七、时间：任务的 timestamp 是毫秒

LLM 被要求输出**带时区偏移的绝对时间**（`2026-08-05T15:00:00+08:00`），
「明天下午三点」这类相对表述由它基于 prompt 里的「当前时间」自己算。
prompt 里的当前时间带**星期和时区**，否则算不对「下周三」。

任务 `due.timestamp` 是**毫秒字符串**（飞书这一族接口里日历用的是秒，
所以这个单位值得单独记一句 —— 写成秒不报错，只会把截止时间排到 1970 年）。
统一走 `actions/time.ts` 的 `toTaskTimestamp`，有测试守着。

`time.ts` 里还有 `localDate` / `wallToMs` 这对墙上时间工具（跨天推进用它们，
不是 `+86400000` —— 有 DST 的时区里一天不一定 24 小时）。
它们现在只被日记的时间范围计算（`diary/range.ts`）用到。

**时间范围不让模型算。** 复盘的范围是七个枚举值之一，窗口由 `range.ts` 算 ——
让模型直接给起止时间的后果不是报错，是一份写着「本周」、实际取了上周记录的复盘。
这和 open_id 是同一条规则：**模型不输出它能悄悄搞错的格式。**

## 七·二、一句话两件事：多步执行

「记一下客户要改 logo，顺便派给张三」是很自然的说法。在只支持一步的年代，
这种句子的结果是 LLM 挑一件做掉、另一件**静默消失**——用户以为两件都办了。

`ParsedIntent` 因此变成 `{ steps: ParsedStep[] }`，dispatcher 顺序执行。
解析层同时收两种形状：单个 `{action, params}`（老形状，逐字节兼容）
和 `{actions: [...]}`。数组里混进编造的动作名时**只丢那一步**，
剩下的好步骤照做——整条作废会让两步里有一步是好的时候用户什么都得不到。

`MAX_STEPS = 3` 是防跑偏的闸，不是能力上限。配套 prompt 硬性规则第 6 条
「只拆用户明确要求的那几件事，不要自己加顺手做一下的步骤」——
**每一步都会真的执行写操作**，模型多加一步就是日志里多一条记录、多建一个任务。

### 截断了必须说出来

超出 `MAX_STEPS` 的步骤被丢掉时，`ParsedIntent.droppedSteps` 记下丢了几步，
dispatcher 在回帖里附一句「⚠️ 只处理了前 N 件事，剩下的请再说一遍」。

早先的实现是**静默截断**，而这恰好是最坏的一种失败：用户说了四件事，
助理回「✅ 已完成」并列出三件——他不会去数，第四件事就这么消失了，
和"一句话两件事"当初要修的问题一模一样。`droppedSteps` 是必填字段
（不是可选的），这样新写解析路径时漏掉上报会在类型层就报错。

### 部分成功必须说成部分成功

某一步失败**不能整体抛错**：前面的步骤已经生效了。只回一句报错的话，
用户不知道日志其实已经记进去了，重下一遍就会记第二条。所以：

- 一步都没成功 → 和以前的单步失败完全等价（`❌ 执行失败：…`）。
  这条路径是**内联处理的，不重新抛给外层 catch**——重抛会让
  `describeFeishuErrorDetail` 跑第二遍并丢掉已经算好的 `error_detail`，
  后台就渲染不出「一键补权限」按钮。
- 成了一部分 → 保留已完成步骤的回复，再加一句
  「⚠️ 但后面这一步没做成（前面的已经生效了，重下指令会重复执行，请只补这一步）」。
  状态记 `failed`：有一件事没办到，不能记成成功。
- 某一步失败后**不继续执行后面的**：多半会以同样的原因失败，
  而每次失败都会在回帖里堆一段权限说明。

日志的 `action` 列存 `"add_diary_record + create_task"`，一步时就是一个动作名。

### `ctx.stepIndex` 是幂等键的一部分

一句话里说了两个任务时，两步共用同一个 `client_token` 会让第二个
被飞书**静默判成重复**——接口返回成功，我们回帖「已创建」，实际只有一个任务。
所以 `createTask` 的 `client_token` 要拼上它。日记记录同理：
`feishu_diary_records` 的幂等键是 `(app_id, message_id, step_index)`，
少了步序号「记一下 A，再记一下 B」的第二条会被当成重复而静默丢掉。
新写动作时如果带幂等键，别忘了这一项。

## 七·三、反问之后：把上一轮带上

「不确定时用 `reply` 问一句」是本模块的取舍底线（误建任务比答一句"没听懂"糟得多）。
但这条路以前是**走不通的**：助理问「你说的会议是几点？」，用户答「下午三点」，
而每条消息都是独立解析的——模型看到的是一句孤立的「下午三点」，
只能再反问一次。用户于是学会了"别理它的问题，重新说一遍完整的话"，
反问功能等于不存在。

`commandLog.ts` 的 `findPriorClarification()` 取上一轮那半截对话，
`parseIntent` 把它作为**真正的 `user` / `assistant` 消息**插在这句话前面
（不是在 system prompt 里叙述一遍——模型需要"合并"两句话，
而叙述会让它把前一轮当成已经结束的历史），另外附一段 `FOLLOWUP_RULE`
说明「这是对你上一问的回答，把信息填进原来那件事然后**直接执行**，不要再问一遍」。
两者缺一不可：只给消息不给规则，模型会礼貌地把问题重问一次。

条件卡得**很死**，每一条都对应一种具体的误伤：

| 条件 | 放宽了会怎样 |
|---|---|
| 同一个 `chat_id` | 在 A 群反问、在 B 群说的话被当成回答 |
| 同一个 `sender_open_id` | 群里另一个人的下一句话被当成回答，指令归到他名下 |
| 10 分钟内 | 半天前那次没答完的反问，会污染今天下午一句无关的话 |
| 上一条的 `action` 必须是 `reply` | **最要紧的一条**。上一条是写操作时带上下文，「再发一条」会把那次发送重放一遍 |
| 上一条 `status = 'done'` | 失败的那轮没有有效的问句，带上只是噪音 |

只带**一轮**，不做多轮会话。整个查询包在 try/catch 里：查不到、查出错都退化成
"按无上文解析"（也就是加这个功能之前的行为），绝不能因为一个增强挡住指令。
模型判断这句话跟上一轮无关时（用户换了话题），规则里明确要求当新指令处理。

## 八、加一个新能力

一个文件 + 一行注册，别的都不用动：

1. 新建 `services/feishuAssistant/actions/yourAction.ts`，导出一个 `ActionDef`：

```ts
export const yourAction: ActionDef = {
  name: 'your_action',
  description: '给 LLM 看的：什么时候该选这个动作',
  params: { foo: '必填。给 LLM 看的参数说明。' },   // 自然语言，不是 JSON Schema
  examples: ['用户可能会怎么说'],
  hint: '一句话告诉用户这个动作能干什么（「我目前会…」清单里的一行）',
  scopes: ['some:feishu:scope'],                    // 会自动出现在接入指引里
  async run(params, ctx) {
    const foo = requireStr(params, 'foo', '某个东西');
    await ctx.client.someApi.create({ ... });
    return { summary: '✅ 干完了：...', data: { ... } };
  },
};
```

2. 加进 `actions/index.ts` 的 `ACTIONS` 数组。

完事。四处都是从注册表生成的：LLM 的 prompt（`intent.ts` 的 `buildSystemPrompt`）、
前端「接入前请开通以下权限」清单（`allRequiredScopes()`）、「用到 XX 时再开」那一段
（`optionalScopeGroups()`），以及没听懂时那句「我目前会…」的能力清单
（`hint` → `capabilityHints()`）。

**权限点默认是"必需"的。** 少数情况下一个动作要的权限贵到不该让所有人在接入时
就去开（目前只有 `im:message.group_msg`），做法是把它加进 `index.ts` 的
`OPTIONAL_SCOPES`，并在 `optionalScopeGroups()` 里写一句「开了它才能用什么」。
注意这是一份**显式清单**，不是"凡不在必需里的就是可选" —— 后者在新增动作时会
静默把一项真必需的权限降级成可选，表现是那个动作**在所有人那里**都缺权限，
而没有一个人被提示要去开。权限点仍然声明在动作的 `scopes` 上（不是删掉），
`diary.test.ts` 有一条断言守着「必需清单里没有它、可选清单里有它、动作上仍然声明」。

**`hint` 是必填的，理由和别的必填字段不同：**能力清单以前是手写在 `dispatcher.ts`
里的一个数组，而手写的那份**必然会过期** —— 日程和私聊发消息删掉之后，
兜底话术还在推销它们，用户照着说一句，换回来的是同一句「没太听懂」，
一条自相矛盾的回复。而没有任何测试会失败，因为那只是一个字符串。

### 数组顺序是**功能**，不是排版

`ACTIONS` 的顺序原样进 prompt 的「可用动作」清单，而模型是顺着读的：
**先撞上一个说得通的就选了**。两条规则：

1. 「建」和它的「改/删」相邻。`create_task` 和 `update_task` 隔得远时，
   「标记完成」会误选 `create`。
2. 语义上容易串味的两组要拉开，并且把**用户更常想要的那个排在前面**。

第 2 条是踩出来的。项目日记原先排在最后（第 9-12 位），`create_task` 在第 3 位，
于是这条真实的三轮对话：

| 用户说 | 选中了 | 回帖 | 实际发生了什么 |
|---|---|---|---|
| 添加新项目，8月飞书skill开发 | `create_task` | ✅ 任务已创建 | 建了一条待办，日志表根本不存在 |
| 创建项目 xzy8 月飞书 skill 开发 | `update_task` | ❌ 没找到对得上的任务 | 什么都没发生 |

第一条最糟：**它看起来成功了**。现在项目日记整块提到 `create_task` 之前。

但位置只改变"先看到谁"，不说明"为什么不是那个" —— 所以还要第二道防线：
`intent.ts` 的 `PROJECT_VS_TASK_RULE`，加上 `create_task` / `update_task`
**自己的描述里**那句排除（「项目不是任务，用 create_diary_project」）。
排除必须写在**被误选的那个动作**上：模型顺着读，看到 `create_task` 时
未必还记得 `create_diary_project` 里说过的话。
两道缺一个都还会串，`intent.test.ts` 的「「项目」和「任务」不能串味」一组守着。

**块内部也有顺序。** 项目日记那六个动作现在是
`create_diary_project` → `rename_diary_project` → `list_diary_projects` →
`add_diary_record` → `review_diary` → `digest_chat`，两条约束都由
`diary.test.ts` 守着：

| 约束 | 排错了会怎样 |
|---|---|
| 改名紧挨着建项目 | 「项目名打错了，改成 X」误选 `create_diary_project`，而那条路只会回一句「本群已经是项目 Y 了」—— 用户以为改名做不到 |
| `digest_chat` 紧跟在 `review_diary` **后面** | 「总结一下」绝大多数时候要的是复盘（读已落库的日志）。反过来排，用户拿到的是一份群聊闲聊摘要，还多花一次额度 |

同样地，光靠顺序不够：这两组也各自在**自己的描述里**点名对方
（`rename_diary_project` 说清「这只改名字」并同时排除 `create_diary_project`
和 `update_task`；`digest_chat` 说清「我读的是群聊原话，读日志请用
`review_diary`」）。

写 `run` 时的几条约定：
- 参数校验用 `requireStr(params, key, label)`，抛出的错误原文会回帖给用户，所以要写人话。
- 涉及"操作某个人"时，只能拿姓名调 `resolvePerson(name, ctx)`（见第六节），
  **绝不接受模型给的 open_id**。解析不出来就抛错，不要挑一个人也不要回落到发言人。
- 涉及"改某个已存在的东西"时，只能拿标题调 `findRecentTarget(...)`（见第八·三节），
  **绝不接受模型给的 guid / record_id**。
- 涉及格式化字符串或计算结果（时间窗口之类）时，让模型答一个**枚举**，
  值在代码里算（`diary/range.ts` 就是这么做的）—— 模型搞错的方式往往不是报错，
  而是产出一个参数不对的东西，而回帖说的是「已创建」。
- 带幂等键（任务是 `client_token`，日记记录是 `(message_id, step_index)` 唯一索引），
  基于 `ctx.messageId` + `ctx.stepIndex`。
- 飞书返回的深链直接透传（任务 `data.task.url`、多维表格的 `url`），
  **不要自己拼** —— applink 的域名在飞书和 Lark 下不一样。
- 分步骤的动作里，"主体已建成、附加步骤失败"要单独处理：建项目时
  「授权给群失败」「关链接分享失败」**都不算整体失败**，而是在回复里说清楚
  （只有 base 本身没建出来才回滚）。否则用户以为没成功、再说一遍，
  而 UNIQUE 索引只会回他一句「这个群已经是项目 X 了」。
- **群聊之外的分支要自己兜住。** dispatcher 已经把私聊挡在外面了（第十·二节），
  但动作里那道 `ctx.chatType !== 'group'` 的闸是这个动作**自己的**前提
  （比如项目的身份就是那个群），不是调度层策略的复述 ——
  哪天策略又变了，这里不该跟着变成一个静默写坏数据的口子。

## 八·二、提示词哪部分能改（应用自己的补充规则 + slot `feishu-intent`）

`intent.ts` 的 system prompt 里有两类东西，只有一类该交给后台：

| 部分 | 来源 | 能后台改吗 |
|---|---|---|
| 动作清单（名称/参数/例句） | 从 `ACTIONS` 注册表**自动生成** | **不能**。改成后台手写，加一个动作就得手动同步一次，漏一次那个动作永远选不中 |
| JSON 输出格式 | 代码写死 | **不能**。格式坏了 `parseIntent` 返回 `null`，表现成「@ 了没反应」——最难查的一类 |
| 只输出姓名、不输出 open_id | 代码写死 | **不能**。删掉这条 LLM 会编 `ou_xxx`，消息发给错误的人（prompt 里根本不给 id，见第六节） |
| 不确定时用 `reply` 问一句 | 代码写死 | **不能**。这是"误建任务 vs 多问一句"的取舍底线 |
| 只拆用户明确要求的步骤（第 6 条） | 代码写死 | **不能**。每一步都会真的执行写操作，放开这条模型会"顺手"多记一条日志、多建一个任务 |
| 「这是对上一问的补充」那一段 | 代码写死，且只在真有上一轮时出现（见第七·三节） | **不能**。没有上一轮时留着它，模型会去找一段不存在的对话 |
| **本群项目现状快照**（项目名 + 最近几条记录 + 在办任务） | 每条指令现算，`diary/context.ts` 的 `renderDiaryContext()`（见 FEISHU_DIARY 第四节） | **不能**。它是数据不是规则；里面**一个 id 都没有**，纯粹为了让模型听懂「那个 logo 的活」指的是哪件事 |
| **本企业的术语、简称、时间习惯** | `feishu_apps.intent_supplement`（059），回落到 skill slot `feishu-intent` | **正是它该在的地方** |

那份快照在 prompt 里的位置也是定的：**`diaryHint()` 之后、补充规则之前**。
`diaryHint()` 是"怎么读这份数据"的说明书，快照是数据本身 —— 顺序反过来时
模型先看到一堆任务行却不知道拿它们干什么，观察到的表现是自作主张去改
快到期的那一条。硬性规则照旧压在最后（快照自带的免责声明也点名引用它们）。

所以这一段是**追加**语义，不是替换。内容作为「## 本企业的补充规则」插进 prompt，
两者都没有 = prompt 与之前逐字节相同。

### 按应用存，不按账号，也不只靠 skill slot

`prompt_skill_bindings` 的**主键就是 `slot` 一列**，`getSkillForSlot()` 查的是
`WHERE slot = ?` —— 全平台一份。而这段内容的全部作用是描述**某一家公司**怎么说话
（他们把「大区会」叫什么、说「下班前」指几点）。一个系统服务多家公司时，
A 公司写的术语会进 B 公司的 prompt，而 B 公司无从知道自己的助理为什么偶尔理解偏了。

所以 migration 059 给 `feishu_apps` 加了一列 `intent_supplement`，用户在
`/feishu` >「助理规则」页自己填：

- **键是 `app_id`（那一行），不是 `user_id`。** 一个账号能绑多个应用，而一个应用
  = 一个飞书租户。按账号存的话，一个代理商账号帮三家公司各绑一个应用时三家又共用
  一段，等于把问题从平台级缩到账号级而没消掉。名册（057）、会话（058）同理。
- **应用填了就用应用的，不叠加平台那份。** 056 播的是**说明性示例模板**
  （里面的术语全是编的），垫在真实规则底下只是噪音，还可能让模型把示例里的假术语当真。
  清空 = 回落到平台默认，不是"没有规则"。
- **一列文本，没接进 skill 注册表。** 注册表有多文件、`{{ref:xxx}}` 展开、enable
  开关、slot 绑定 —— 那是给平台做提示词工程的机械，而且它在 `/api/admin/*` 下，
  普通用户根本进不去。企业用户要的只有一件事：写下我们公司怎么说话。
- **单独一个 `PUT /apps/:id/intent-supplement`，不并进 `POST /apps`。**
  后者是整行替换语义，而前端有好几处只带部分字段就调它（停用/启用、从提示里
  一键放行某个群）。挂上去的话任何一次这种调用都会把用户写了半天的那段话清成空串，
  而且几天后才会被察觉（"助理忽然听不懂话了"）—— 和白名单「保存时静默丢掉没列出来
  的 id」是同一类事故，只是更难发现。`feishuAssistantRoutes.test.ts` 有用例守着。
- **改完不用重连。** `connection.ts` 每条消息都重取一遍应用行（`current`），
  下一条指令就按新规则理解。
- **有 4000 字上限。** 不是防滥用，是防自伤：这段话每条指令都随 prompt 发一次，
  塞一份员工手册进来会让每条指令都更慢更贵，而长文本还会把后面的硬性规则压下去 ——
  表现是助理"忽然开始乱建任务"，没人会想到是那个文本框。

`GET /capabilities` 里的 `default_supplement` 是"没填时实际生效的那份"，
前端「填入示例模板」按钮读它。客户端自己抄一份的话，平台改了模板之后按钮填出来的
还是旧的，而用户以为那就是当前默认。

两个实现上的讲究：

- **插在硬性规则之前**。LLM 对后文指令更敏感，硬性规则必须压在最后一段 ——
  否则一条随手写的补充规则就能盖掉 open_id 约束。这条对来自应用的内容尤其要紧：
  那是终端用户的文本框，他写什么都可能。
- **配套那条优先级声明（硬性规则的最后一条）跟着补充规则一起出现或消失**。
  有人会写「open_id 可以自己推断」，所以需要一条"冲突时以前面几条为准"兜底；
  但没有补充规则时留着它，prompt 就指向一个不存在的章节。
  `supplementParts()` 同时返回这两段，`intent.test.ts` 有测试守着。
  它引用的条数**不要写死在测试里**：加一条硬性规则时那条声明的编号要跟着走，
  而声明写「以第 1-5 条为准」而实际有 6 条时，第 6 条就悄悄落进了 skill
  能覆盖的范围——测试改成从实际规则条数推导出应引用的上限。

migration 056 播了一份带注释示例的模板并默认绑定（术语翻译、时间习惯、部门倾向），
示例全部是说明性的，不改也不影响行为 —— 它现在的角色是**没填时的默认值**，
以及「助理规则」页那个「填入示例模板」按钮的内容来源。写它的时候记住：
**这里只写"怎么听懂人话"**，写输出格式或动作相关的规则无效，写错了还可能干扰解析。

## 八·三、改/删已有的东西：「哪个任务」比调哪个接口难得多

`update_task` 要的是 `task_guid`，而**模型不可能知道它**。这和 open_id 是同一类问题
（第六节），所以用同一套解法：**id 绝不经过 LLM，只从代码控制的来源里取。**

编 guid 比编 open_id 更隐蔽：编出来的大概率 404，但**万一命中**就是动了别人的
任务，而回帖会说「已完成」。

**来源有两个，顺序是有讲究的**（`updateTask.ts` 的 `resolveTarget`）：

| 顺序 | 来源 | 覆盖 | 窗口 |
|---|---|---|---|
| 1 | `feishu_project_tasks`（068） | 068 之后建的所有任务，带状态和起止时间 | **不限 7 天**，最多回看 200 行 |
| 2 | 执行日志（`commandLog.findRecentActionResults` → `actions/recent.ts` 的 `findRecentTarget`） | 068 之前建的任务（只存在于日志里），以及别的动作的目标反查 | 7 天 / 50 行 |

先库后日志，是因为库那份能回答日志答不了的问题（一个季度前派的活、
「logo 那个做完了吗」）。日志那条路留着**不是**兼容包袱：任务表里没有的东西
（历史任务、别的动作的目标）仍然只能从那儿找，而两条路的歧义规则是同一套。

### 范围是「本应用 + 本发言人」，不含会话
「那个任务」指的是**我让助理建的**那个，跟他当时在哪个群说的没关系（在 A 群派的任务，
回头在 B 群里说「标记完成」很自然）。但 app 和发言人这两条一条都不能少：
跨应用是跨企业，跨人是改别人的东西。

走任务表那条路时，「本发言人」是 `created_by = ? OR owner_open_id = ?`
两者**取并集**：项目群里 A 派给 B 的活，B 说一句「那个任务做完了」是最自然的说法，
只按 `created_by` 筛会让负责人本人找不到自己的活。

### 关键词匹配前先去掉所有空白
中文里空格可有可无，同一个标题两次说出来空格位置常常不一样（建的时候输入法
自动加了、改的时候顺手打的）。不归一化的表现是一句**自相矛盾**的回帖：

> 没找到和「xzy8月飞书skill开发」对得上的任务。我最近帮你建过这些：
> · xzy8 月飞书 skill 开发

用户看到自己要的东西就列在那儿却说找不到，只会认定助理坏了。
`recent.ts` 的 `norm()` 对标题和关键词都做「小写 + 去掉所有空白」。
**只吃空白，不放宽成模糊匹配** —— 多个候选照旧拒绝（下面「歧义绝不自己挑一个」）。
库那条路上是 `store.ts` 的 `normKeyword()`，同一套规则的第二份实现
（两处都写了「改一处要改两处」）：只改一处的表现正是上面那句自相矛盾的回帖 ——
只是它现在只出现在两条来源中的一条上，更难复现。

**不能复用 `findPriorClarification`**：那个函数的 `action = 'reply'` 闸门是故意的
（不让上下文越过写操作），语义正好相反。

### `failed` 的指令也算候选
`result` 里只有**成功的那几步**。一条"建任务 + 记一条日志"在第二步失败时整条记
`failed`，但任务是真建出来了 —— 不收它的话，用户明明看到任务在飞书里，
助理却说「我没帮你建过任务」。

### 改动作自己也在 `actions` 列表里
改过标题之后，用户会用**新**名字称呼它，而新标题只在 `update_*` 那行日志里。
所以 `findRecentTarget` 的 `actions` 要同时列 create 和 update，并按 id 去重
（日志是 `created_at DESC`，留下的自然是最新那行、最新的标题）。

### 加删除类动作时要把「墓碑」加回来
`findRecentTarget` 曾经有一个 `deletedBy` 参数，把已删掉的东西从候选里剔掉。
删日程动作一起删掉之后它没有调用方了，所以也删了（一个没人用的参数会让人以为
这件事已经被处理了）。

**现在一个删除类动作都没有，所以删过的东西仍然会留在候选里** ——
再加一个删除动作时必须把墓碑加回来，因为这条路上的失败全都长得像成功：
用户删完再说「那个改一下」，我们会拿一个死 id 去 patch；说「再删一次」则会
真的执行第二次删除（连带它的通知），而回帖说的是「已删除」。
068 之后这件事要做**两遍**：日志那条路要墓碑，任务表那条路要一个"已删除"的
状态位（或者真删行）。只补一边的结果是"删掉的任务只在其中一条来源里消失"，
而哪条来源命中取决于任务是哪年建的。眼下「不想干了」的正解是
`status = 'cancelled'`（甘特图上灰掉，历史仍在）。

### 歧义绝不自己挑一个
和 `resolvePerson` 同一条原则，而且这里**连"取最近那个"都不行**：「那个任务完成了」
里的"那个"指的是他心里想的那件事，不一定是时间上最近的一件。命中多个、或者
没给关键词又有多个候选时，一律把候选列出来让他重说。

### 「找不到」的话术是硬性要求
必须写成「**我只能改我自己帮你建的那些**」，不能写「没找到这个任务」。
原因见第五节的身份模型：任务系统视角下 tenant token 就是另一个普通用户，
`task.list` 只返回调用身份自己创建的东西，所以用户手动建的任务我们拿到的
不是"报错"，而是**安安静静的空**。说"没找到"会让用户以为是搜索没搜到，
反复换措辞重试；说清限制他才知道该去飞书里自己改。

### 一个动作，四个接口，必然可能部分成功
飞书把任务的后续操作分在四个接口上：`task.patch`（标题/截止/完成状态）、
`addMembers`（协作人）、`addReminders`（提醒）、`comment.create`（评论，
guid 走 `data.resource_id` 而**不是** path）。所以 `update_task` 是多次调用，
处理方式和多步执行一样（第七·二节）：做完所有能做的，然后把成功的和失败的
一起说清楚，并明说「上面那几条已经生效了」。中途 throw 会留下"改了一半、
不知道改到哪"的状态，而用户整条重下会把成功那半再做一遍。

`update_fields` 是 `task.patch` 的核心约定：**只有列在里面的字段会被改**，
而列了名字却没给值 = 把那个字段清空。两者必须严格配对，绝不能"顺手多列一个"。

### 姓名解析放在所有写操作之前
all-or-nothing：解析失败就整个抛错，一个字段都没改。反过来的话用户会得到
「截止时间改好了，但张三没加上」，而他重下指令又会把截止时间再改一遍。

### 几件必须说出来的事
- 设任务提醒要求任务**先有截止时间**，而飞书的报错不会说这件事，所以要自己补一句。
  另外任务只支持**一个**提醒（改提醒要先 `removeReminders`）。

## 八·四、错误怎么变成用户能照着办的一句话

SDK 的错误处理是：把格式化好的详情**打进 logger**，然后 `throw e` 抛出**原始的
AxiosError**（`node_modules/@larksuiteoapi/node-sdk/lib/index.js`，
`.catch((e) => { this.logger.error(formatErrors(e)); throw e; })`）。

于是 `e.message` 永远只有 `Request failed with status code 400`，
而缺哪个权限、去哪申请全都埋在 `e.response.data` 里。直接把 `e.message` 回帖
等于没回 —— 用户看不到服务端日志，这是他唯一的信息来源。

`feishuError.ts` 负责这一层翻译，产出 `FeishuErrorDetail`：

| 字段 | 用途 |
|---|---|
| `kind` | `scope_denied` / `contact_scope_empty` / `availability_denied` / `api_error`。前端据此决定渲染哪种引导（见下表） |
| `message` | 回帖 + 日志展示的人话 |
| `scopes` | 缺的权限点。**多项时是「任一即可」**（飞书 99991672 的语义），写成「都要开」会让用户白开一个 |
| `apply_url` | 一键授权页地址 |
| `code` / `log_id` | 转给管理员时能直接在飞书后台查 |

关于 `apply_url` 的两点：

- **优先透传飞书 msg 里给的那个**，因为 applink 域名分 `feishu.cn` / `larksuite.com` 两套。
- 但飞书**不是每次都给**（不同接口、不同网关版本表现不一致）。而「点一下去开权限」
  恰恰是这类失败唯一需要的操作，所以 msg 里没有时用 `app_id + scopes` 兜底拼一个：
  `https://open.feishu.cn/app/{app_id}/auth?q={scopes}&op_from=openapi&token_type=tenant`。
  这也是 `ActionContext` 里有 `appId` 的原因 —— 动作内部自己 catch 的错误
  （如 `updateTask` 加关注人失败、建项目时授权给群失败）走不到 dispatcher 的收口，
  得自己拼。

**权限提示必须带上「开通后要发布版本」**。只开权限不发版时，飞书返回的错误和
完全没开一模一样，用户会以为按钮没生效然后开始怀疑代码。这是本模块头号坑。

### 飞书有三套互不相干的设置，报错却都长得像「没权限」

这是接入期最耗时间的一类问题：用户打开错误的页面，看到一切正常，然后开始怀疑代码。
所以三者必须是三个 `kind`，各自把用户导到对的地方。

| code | 含义 | 在飞书后台的哪 | `kind` | `apply_url` |
|---|---|---|---|---|
| `99991672` | 权限**点**没开 | 权限管理 > **API 权限** | `scope_denied` | `/auth?q=<scopes>` |
| `40004` | 通讯录**数据权限**范围是空的 | 权限管理 > **数据权限** | `contact_scope_empty` | `/auth`（**不带 q**） |
| `230013` | 对方不在应用**可用范围**里 | 应用发布 > **版本管理与发布** | `availability_denied` | `/publish` |

- **40004 的 `apply_url` 故意不带 `q=`** —— 那个参数是"勾选这几个权限点"的意思，
  而权限点用户已经配好了。带上它会打开一个全是绿勾的页面。
- **230013 指向 `/publish` 而不是 `/auth`** —— 可用范围根本不在权限页。
  它还必须说清「新建应用默认只有创建者本人可用」：这是第一次把任务派给同事时的
  **必经错误**，不说明的话用户会以为自己哪里配错了。飞书的原文
  `Bot has NO availability to this user` 是英文的，且一个字都没提「可用范围」。
- `isScopeDenied` 保持只认 `99991672`，`isContactUnavailable` 只多认 `40004`
  （因为那两个的后果相同：读不到通讯录）。230013 不在其中 —— 它不影响名册同步。

前端渲染在 `client/src/components/feishu/FeishuErrorDetail.vue`，用户侧和后台共用：
上面三个 `kind` 各是一张卡片（各自的标题、指引句、按钮文案、深链），
按钮旁都有「复制链接」——管理员看到的失败往往要转给有那个应用权限的同事去点；
`api_error` 照旧 `<pre>` 展示原文。**前端不解析错误文本** —— 那样每次飞书改一版文案就会静默失效。
新增一类 code 时是「加一个 `kind` + 加一张卡片」，不是在文案里加一句 if。

## 九、数据表（migration 053 / 055 / 057 / 058 / 059 / 066 / 068 / 069）

| 表 | 作用 | 要点 |
|---|---|---|
| `feishu_apps` | 绑定的自建应用 | `app_id` 上有 **UNIQUE 索引** —— 两行就是两条连接，同一条消息被处理两遍。`app_secret` 是 AES-GCM 密文。057 加了 5 个 `dir_*` 列，059 加了 `intent_supplement`（本企业的补充规则，见第八·二节） |
| `feishu_events` | 去重 | `message_id` 作主键；7 天清理（cron，不是启动时） |
| `feishu_commands` | 指令日志 | 排障唯一依据，见下。`error_detail`（055）存 `FeishuErrorDetail` 的 JSON。14 天保留期 |
| `feishu_directory_users`（057） | 名册 | 主键 `(app_id, open_id)`；`(app_id, match_key)` 上有索引 —— 按名字找人在执行路径上 |
| `feishu_directory_departments`（057） | 部门树 | 主键 `(app_id, department_id)`。只用于展示和给人打部门标签 |
| `feishu_chats`（058） | 机器人见过的会话 | 主键 `(app_id, chat_id)`。让白名单可以勾选，见下。一行一个群，天然有界，不需要清理 |
| `feishu_diary_*`（066 / 069） | 项目日记 | 四张表（总表 / 项目 / 记录 / 复盘）。069 给记录加了 `origin`（`manual` \| `chat_digest`，区分「谁的原话」和「AI 归纳的」）和 `digest_range`（同一段时间总结到第几版）。用法和设计见 [FEISHU_DIARY.md](./FEISHU_DIARY.md)；隔离键同样是 `app_id` |
| `feishu_project_tasks`（068） | 项目派活 | 本模块唯一**会被更新**的业务表，也是甘特图的数据源。`project_id` **可空**（没绑项目的群里派的活也要落库）；起止时间是**毫秒**；`status` 是代码枚举（`diary/taskStatus.ts`）。幂等键是 `(app_id, message_id, step_index)` 上的**部分**唯一索引 —— 历史行的 `message_id` 是 `''`，全量索引会让它们互相撞 |

`error_detail` 存 JSON 而不是拆成三列：这份数据只被前端整体读取、从不参与
`WHERE` / `ORDER BY`，而字段还会随新动作增加。`GET /commands` 会把它解开成对象再返回
（坏 JSON 当 `null`，一行坏数据不该让日志页打不开）。

名册表的三个设计决定：

- **按 `app_id` 隔离，不按 `user_id`**。一个应用 = 一个飞书租户；两家公司的
  通讯录混在一张表里会让「李四」跨租户命中。解绑时按 `app_id` 清理
  （`deleteApp` 里做，没有外键级联），否则重新绑定同一个应用会拿到一份
  可能过期几个月的旧名册，而界面显示「从未同步」。
- **`match_key` 独立成列**，不在查询时用 SQL 函数算：能走索引，而且写入和查询
  共用同一个 `normalizeName()` —— 分开实现会出现「存进去了但查不到」且不报任何错。
- **`department_names` 冗余存拼好的字符串**，不查询时 join：它只在同名歧义时
  用来告诉用户「哪个张三」，部门数据只在同步时变，而读路径在指令执行的关键链路上。
- **离职的人保留在表里**（`is_resigned`），因为「此人已离职」和「通讯录里没这个人」
  对用户是两种完全不同的处置；但**从通讯录移除**的人会随整批替换消失。

`feishu_apps` 上的 5 个 `dir_*` 列（`dir_sync_state` / `dir_sync_error` /
`dir_sync_at` / `dir_user_count` / `dir_source`）和 `conn_state` 同理：
同步是后台跑的（接口返回 202），用户点完按钮之后只能靠这几个字段知道成没成。

### `feishu_chats`：chat_id 在飞书客户端里看不到

群白名单存的是 `oc_xxx`，而这串 id 在飞书界面上**没有任何地方能看到**。
于是在这张表之前，配白名单的唯一可行路径是：先把白名单留空（= 真的不设防）→
在群里 @ 一次 → 去指令日志里把 id 抄出来 → 回来粘上。中间那步"不设防"是真的，
而最后一步基本没人回来做。

两个写入口，对应用户会遇到的两种情形：

- `recordBotAdded`（`connection.ts` 收到 `bot_added` 事件）—— 有群名，最好的情况。
  群名要 `im:chat:readonly` 才拿得到，而它不是必需权限，所以经常是空的：
  **新名字为空时不要盖掉旧的**，否则第二次被拉进同一个群会把那次查到的名字抹掉。
- `recordRejected`（白名单外被拦时）—— 只有 id，但至少能告诉用户"这个群在敲门"。
  **刻意不写 `feishu_commands`**：那张表是"已受理指令"的日志，而这条消息恰恰
  没有被受理（没花额度、没调 LLM）；更实际的问题是任何人把机器人拉进群
  就能往别人的日志里灌行。所以这里只在会话维度累加一个计数。

`GET /apps/:id/chats` 返回每个会话 + 一个**服务端算的** `in_allowlist`
（白名单为空 = 全部放行）。这条规则不交给前端：用户侧和后台各实现一遍，
迟早有一个算错，而算错的方向是"显示已放行"——用户以为自己设好防护了。

前端据此把白名单从"手打 chat_id"变成勾群名，并在应用卡片上直接说
「「产品群」@ 过 7 次，都被群白名单拦下了」+ 一个「放行这个群」按钮。
被拦时机器人是**不回话**的（回了等于向任意群暴露自己），所以用户那边只看到
"@ 了没反应"，不在这里说他就会一路去查连接状态和飞书权限。

表单里还要列出**白名单里有、但清单里没有**的 id 并保持勾选：只渲染清单的话，
一次保存就会静默删掉它们，表现是一个本来正常的群突然不响应了。

### `feishu_diary_*`：网页侧三个路由，全部只读

```
GET /apps/:id/diary/projects                        项目清单 + 项目总表链接 + 每个项目的统计
GET /apps/:id/diary/projects/:projectId/records     日志正文，最新在前
GET /apps/:id/diary/projects/:projectId/summaries    历史复盘，summary 是完整版
```

存在的理由和 `feishu_chats` 同类：那几张多维表格**在飞书里搜不到**（建表时没传
`folder_token`，链接分享又是主动关掉的），链接被群消息刷走之后就找不回来了。
群里 @ 助理说「有哪些项目」能问回来，但那要求你在群里；这三个路由是网页侧的入口，
前端渲染成 `/feishu` >「项目日记」。

三件事写在代码注释里，这里再点一次：

- **只读是设计，不是没做完。** 同步是**只追加**的（推上去就置状态位，永不重推），
  所以「网页删掉的这条，表格里那行怎么办」只有一个答案：删不掉。
  开一个网页写入口就等于让库和表永久不一致，而用户看的是表。
  所有写路径都走群里 @ 助理 —— 那条路每一步都带记录人、时间、原始 `message_id`。
- **`:projectId` 必须同时校验 `app_id`。** 光按 id 查的话，拿到一个别家公司的
  `project_id` 就能读到那家公司的全部项目日志；不匹配就 404。归属校验用
  `appForDiary()`（403 的文案是「无权查看」）—— 日志正文是那家公司的项目进展，
  越权读这里比越权改配置更糟。
- **`unsynced_count` / `unsynced_task_count` 必须露在页面上。** 补推是跟着
  **下一次记录**发生的（没有定时任务），所以一个不再活跃的群会永久停在
  "库里有、表里少几条"的状态。不显示这个数字的话，那种缺失查不出原因。
  记录和任务是**两条**同步路径，所以库里是两个字段；`/admin/feishu` 那一列
  把它们相加成一个数（那一列只回答「表里缺东西吗」），用户侧则分开显示。
- **`origin` 也必须露出来。** 记录接口返回 `origin`（`manual` / `chat_digest`）：
  这张表的全部价值在「当时到底怎么说的」，而 AI 从群聊归纳出来的条目和原话
  并排放着 —— 分不出来的话整张表就不能当证据用了。正文里有
  「【群聊摘要 MM-DD】」前缀，但那是给飞书表格用的兜底（多维表格那侧不加新列，
  见 FEISHU_DIARY 第六节），网页端要能据此单独标记和筛选。

`projectStats(appId)` 用三条 `GROUP BY` 一次算完所有项目的九个统计字段，
不是每个项目查六次 —— 这个接口是页面打开就调的。两个坑：
`DiaryProjectStats` 的初值只有 `emptyStats()` 一份，路由里
**不要抄一份字面量**（抄的那份不跟着加字段，任务数和摘要数就是这么漏的，
而漏掉的键在前端读成 `undefined`、渲染出来和「有数据但是 0」一模一样）；
任务那条查询必须带 `project_id IS NOT NULL`，否则没绑项目的群里派的活会被
`GROUP BY` 凑成一格、键是 `null`，前端照着渲染出一个叫 "null" 的假项目。

凭证挂在 `user_id` 上而不是全局单例，理由和 `feishuBitable.ts` 一样：
自建应用只在创建它的企业内可用，天然是"一个租户一套凭证"。
附带好处是 AI 额度归属直接落在这个账号上，migration 052 的专属渠道机制原样复用。

## 十、排障顺序

`@` 了没反应时，按这个顺序看（后台 `/admin/feishu` 或用户侧 `/feishu` 的指令日志）：

1. **指令日志里根本没有记录** → 事件没进来。**先看应用卡片上有没有
   「某个群 @ 过 N 次，都被群白名单拦下了」**——被拦是静默丢弃（设计如此，
   回话等于向任意群暴露自己），这是"没记录"最常见的原因，页面上有一键放行。
   排除它之后再看应用的连接状态；看飞书后台的权限是否**已发布版本**
   （权限不发版不生效）；看事件订阅方式是否选了「长连接」并添加了
   `im.message.receive_v1`。
2. **有记录、状态 `ignored`** → 收到了但没听懂。看原文，可能确实说得太模糊
   （提示语会引导用户补充），也可能是 LLM 没返回合法 JSON。
   如果是**公司内部叫法**没听懂（「过一下方案」被当成派任务），那不是 bug ——
   去 `/feishu` >「助理规则」把这句话的意思写下来（第八·二节）。
   反过来，**本来好用的忽然理解偏了**，第一件要看的也是这段规则被改成了什么。
3. **状态 `failed`** → 调飞书接口报错，错误原文在日志详情里，
   同时也已经回帖给用户了。最常见的三种都在飞书后台，但**是三个不同的页面**
   （见第八·四节的表）：`99991672` 权限点、`40004` 通讯录数据权限、
   `230013` 可用范围。日志详情里会直接给对应那一页的按钮，
   点完**记得发布新版本**。
   只有「总结群聊」失败、别的动作都正常时，看的是**可选权限**
   `im:message.group_msg`（第八节）—— 它故意不在接入清单里，所以第一次用必然失败，
   而这不是配置漏了。
4. **状态一直 `pending` / `running`** → 正常情况下不该看到：启动时
   `reapZombieCommands()` 会把上一次运行遗留的这两种状态标成 failed
   （理由和 `core/jobs.ts` 的 `reapZombieJobs()` 一样——这些指令全靠内存里那个
   游离 promise 驱动，进程一没就必然死了，绝不会有人再来推进它们；
   而日志里挂着一行 `running` 会让用户以为"还在办"，继续等一个永远不会来的结果）。
   所以真看到了，说明它是**这次运行里**的：要么正在跑（几秒内会变），
   要么卡在一个不超时的调用上（见第三节末，LLM 已经限到 120s）。
5. **回帖是「⚠️ 只处理了前 N 件事」** → 一句话说了超过 `MAX_STEPS = 3` 件事，
   多的被丢了。让用户把剩下的再说一遍，不是 bug。
6. **回帖是「太忙没排上队」** → 并发闸的队伍满了（见第三节）。
   本次一个写操作都没执行，重说一遍是安全的。持续出现说明该调 `MAX_CONCURRENT`，
   调之前看 `ai_logs` 里的耗时分布。
7. **错误是个 JS 报错（`xxx is not defined` 之类）而不是飞书报错** →
   开发期改坏了代码，dev server 热重载了一份半成品。看时间戳对不对得上，
   别当成飞书的问题查。

半夜断线怎么自愈：`connection.ts` 的看门狗每 5 分钟把「库里启用的应用」和
「实际活着的连接」对齐一次。SDK 的 WSClient 自己会重连，但**重试次数有上限**：
网断十分钟耗完之后它就彻底躺平，而进程还活得好好的——服务在跑、页面正常、
`conn_state` 停在 `failed`，所有人 @ 都没反应且指令日志一条记录都没有。
没有这个巡检时唯一的恢复手段是有人正好想到去点「重连」，而这类故障最可能
发生在半夜、最可能被发现于第二天早会。

判据是 `connectionStatus()`（SDK 自报的状态），不是 `conns` 里有没有这一项——
躺平的连接对象仍然在 Map 里。`connecting` / `reconnecting` 不打断（重建会扔掉
SDK 当前的重试进度）。反向的不一致同样要处理：**连着但库里已停用/删除的要断开**，
漏掉这步的后果是被停用的应用仍在处理指令、仍在烧那个账号的额度，而界面显示"已停用"。

## 十·二、只在群聊里工作

助理**只处理群消息**，私聊一律拒绝（`dispatcher.handleMessage` 的第一道闸，
返回 `'p2p_rejected'`）。三个理由：

1. **私聊没有任何闸。** 群白名单只管群聊，而私聊从来没有对应的限制 ——
   同一租户里的任何人私聊机器人就能烧掉绑定账号的 AI 额度，
   而且私聊不进 `feishu_chats`，用户连"谁在用"都看不到。
2. **私聊能做的事本来就是群聊的真子集，失败方式却更多。**
   项目建不了（项目的身份就是那个群）、记日志/复盘必须手打项目名、
   `@` 不到人只能靠名册 —— 一个"能用但处处别扭"的入口。
3. **指令留在群里是产品意图。** 同事能看到谁让助理做了什么。

### 拒绝要**说出来**，所以不用 SDK 的 `dmMode: 'disabled'`

SDK 支持在 LarkChannel 内部就把私聊丢掉，但那是**静默丢弃** ——
用户私聊机器人后什么都收不到，而"没反应"和"助理坏了"完全同形
（本模块的第一条原则）。所以 `policy.dmMode` 仍然是 `'open'`：
消息照收，由 dispatcher 回一句「我只在群聊里工作，请到群里 @ 我」。

代价是私聊消息仍会进到进程里（占一次 `claimEvent` 写库），
但**不花 AI 额度**：那道闸在意图解析之前。
去重同样要走 `claimEvent` —— 飞书成功也重推，少了它用户会连收五条一样的拒绝。

和白名单外群聊的处理**刻意不同**：那种情况是静默拦（回话等于向任意群暴露
自己的存在，所以只在 `feishu_chats.reject_count` 上累加计数给后台看），
而私聊的人是特意来找机器人说话的，必须给他一句话。

两处都**不写 `feishu_commands`**：那张表是"已受理指令"的日志。

## 十一、其他限制

- 群里必须 @ 才响应（`policy.requireMention: true`）；**私聊不处理指令**（见第十·二节）。
- **@所有人不触发**（`respondToMentionAll: false`）—— 那通常是通知全员，不是下指令。
- 群白名单为空 = 不限群。首次接入时用户还不知道自己的 chat_id，强制填会卡在第一步；
  但机器人被拉进任何群都能被 @ 并消耗本账号额度，所以 UI 上明确提示试通后回来填。
  填法是**勾群名**，不是手打 id（`feishu_chats`，见第九节）。
- 速率限制：任务创建 **10/s** 是最紧的一档；im 消息每个群 5 QPS（所有机器人共享）；
  多维表格写行也有配额，所以日志同步失败是限流的正常表现，欠的行跟着下一次记录补推。
- **一条指令最多拆 3 步**（`MAX_STEPS`，见第七·二节）。「记一条日志 + 派个任务 + 复盘」
  是上限，再多的只保留前 3 步，**并在回帖里明说丢了几步**。
- **同时最多 4 条指令在解析**，另外最多排 20 条（`concurrency.ts`，见第三节）。
  排不上队的会被明确拒绝，而不是无限等待。
- **反问只能接一轮**（见第七·三节），且必须是同群、同一人、10 分钟内。
  更早的那轮反问不会被接上，用户得把话说完整。
- **本企业的补充规则最多 4000 字**，且只影响"怎么听懂人话"（第八·二节）。
  动作清单、JSON 格式、open_id 约束都在代码里，写在那个文本框里无效。
- 指令不明确时 LLM 被要求用 `reply` 动作回一句"需要你补充什么"，
  而不是硬挑一个写操作 —— 误建一个任务比答一句"没听懂"糟糕得多。
- **名册是快照，不自动更新**。有人入职/离职/调岗后要回来手动同步一次。
  代价是「刚入职的人找不到」，换来的是指令执行路径上零 API 调用（3 秒限制）。
- **列任务做不到**（`task.list` 要 user token，见第五节）。面向用户的读动作有三个：
  `list_diary_projects` / `review_diary` 读我们自己的库，`digest_chat` 读群聊原话
  （唯一一个读飞书的）。项目派了哪些活是**在多维表格的「任务」表和甘特图里看**，
  不是在群里问回来的。
- **总结群聊一次最多读 3 天**（`chatDigest.ts` 的 `MAX_DAYS`），只给
  今天 / 昨天 / 最近 N 天三个窗口。要更长的范围一律拒绝并说明理由 ——
  放开的后果不是报错，而是读了 500 条、只用了最后 200 条，
  产出一份写着「本月」实际只覆盖半天的摘要，而它会落进日志表。
- **`im:message.group_msg` 是可选权限**（第八节），没开的时候只有「总结群聊」
  一个功能失败，别的照常。第一次用会失败，但报错是翻译过的「缺哪个权限 + 一键申请」。
- **只能改助理自己建过的任务**。068 之后建的在 `feishu_project_tasks` 里
  **不受 7 天限制**（最多回看 200 行）；更早的只在指令日志里，窗口是
  **7 天 / 50 条**（`LOOKBACK_MS` / `LOOKBACK_ROWS`，见第八·三节）。
  用户手动建的两条路都看不见，回帖会明说这一点而不是含糊成「没找到」。
- 说不清是哪一个时（同名多个、或者只说了「那个任务」而有多个候选）**一律拒绝**，
  把候选列出来让他重说 —— 连"取时间上最近的那个"都不做。
- **任务只支持一个提醒**，且任务必须先有截止时间；改提醒要先删旧的（飞书的限制）。
- **没有任何删除类动作**（任务、日志、项目都删不了；项目**能改名**）。
  任务不想干了用 `status = 'cancelled'`。所以 `findRecentTarget` 眼下不需要墓碑，
  加删除动作时要一并加回来，而且**要在两条来源上各做一次**（见第八·三节）。
- **没有任何定时任务。** 群聊摘要要人在群里说一句才生成，多维表格的补推是跟着
  **下一次记录**发生的。清理类的 cron（`feishu_events` 7 天、`feishu_commands` 14 天）
  是另一码事，不碰业务数据。
