# 项目日记使用教程

在飞书群里 @ 助理说一句「记一下：……」，这句话就进了这个项目的日志表；
说一句「指派给 @张三 一个任务，今天开始，3 天后完成」，任务落到他的任务中心，
同时进这个项目的甘特图；想知道这段时间干了什么，说一句「复盘一下本周」，
助理把日志取出来交给 AI 归纳，总结发回群里，同时存进表格。
连日志都懒得记的时候，说一句「总结一下今天群里聊了什么」，
助理去读群聊原话，自己挑出该记的几条写进日志。

一句话概括这个功能的形状：**一家公司一份项目总表，一个群一个项目，一个项目一张日志表。**

> 这是「飞书助理」（`/feishu`）里的一组能力，不是独立模块 —— 用法、权限、
> 排障方式都和其他指令（建任务、约日程）一样。助理本身的接入见
> [FEISHU_ASSISTANT.md](./FEISHU_ASSISTANT.md)，本文只讲项目日记。

## 一、开始之前

### 1. 助理本身要先接好

去 `/feishu` 绑定你公司的飞书**自建应用**，状态显示「已连接」。
没绑过的先看那个页面的「接入指引」走完五步（建应用 → 加机器人 → 事件订阅选长连接 →
开权限 → 放开可用范围）。

### 2. 权限点要多开两个

项目日记要建多维表格、要收链接分享、要把表授权给群，所以除了助理原有的权限，
飞书后台的「权限管理」里还得有这两项：

| 权限点 | 少了它会怎样 |
|---|---|
| `bitable:app` | 建不出多维表格，「新建项目」直接报错 |
| `drive:drive` | 表能建出来，但**群里谁都打不开**（显示无权限），链接分享也关不掉 |

`/feishu` >「接入指引」页上那份权限清单是从代码里的动作注册表自动生成的，
照着它勾就不会漏。

### 还有一组是**可选**的：读群聊记录

只有[「总结群聊」](#四二总结群聊)这一个功能要用到，不开也能用其余全部能力：

| 权限点 | 说明 |
|---|---|
| `im:message.group_msg` | 「获取群组中所有消息」。**飞书这一档最难批**，后台要额外填用途说明 |
| `im:message:readonly` | 读消息内容 |

刻意**不**把它们写进「绑定前请先开通」那份清单：那会让每个人的接入流程都卡在
最难批的一步上，而这个功能大部分人用不到。代价是第一次说「总结一下群里聊了什么」
会失败 —— 但失败回帖里写着缺哪个权限、附一键跳转，照着开完发版就好。
`/feishu` >「接入指引」页上这组单独列在必需清单下面，标着「用到 XX 时再开」。

> ⚠️ **改完权限一定要「创建并发布新版本」**，否则不生效。这是飞书最常见的坑：
> 后台里权限已经是绿的，接口仍然报 `99991672`。

### 3. 把助理拉进项目群

项目是**跟群绑定**的，所以助理必须在那个群里。顺手确认一下 `/feishu` 的群白名单：
白名单为空 = 不限群；填了的话要把这个项目群勾上，否则在群里 @ 它不会有任何反应
（被拦下的次数会显示在应用卡片上，那里有一键放行）。

## 二、第一次用：建项目

在项目群里 @ 助理：

```
@助理 新建项目：印度纪录片
```

也可以说「建个项目叫春节品牌片」「这个群立个项目，叫客户A改版」——
不用记固定句式，助理会理解。

助理回你：

```
✅ 项目 印度纪录片 已建好。
以后在本群 @ 我说「记一下……」就会记到这个项目的日志表里；说「复盘一下」我来总结。
[项目日志表](https://…/base/bascn…?table=tbl…)
[项目总表](https://…)（全公司的项目清单，只有你能打开）
表已开放给本群（只读）：日志只能通过 @ 我来记，这样每条都有记录人和时间，也不会被误删。
（链接找不到了就 @ 我说「有哪些项目」。）
```

**这两个链接要留一下** —— 表格不在你的云文档空间里，链接是唯一入口
（找不回来的话说「有哪些项目」，见[第五节](#五生成的几张表长什么样)）。

**这一步背后做了四件事**：

1. 在你公司的飞书云文档里建一个多维表格，里面三张表：「记录」「复盘」「任务」
   （「任务」表上还有一个**甘特图**视图，见[第三·二节](#三二任务与甘特图)）；
2. 把这张表授权给本群（**只读**），并关掉链接分享；
3. 如果这是公司的第一个项目，顺手把「项目总表」也建出来 ——
   **没有「请先初始化」这一步**，你不需要做任何准备动作；
4. 把这个项目登记进项目总表（项目名、日志表链接、关联群聊、创建人、记录数）。

### 一个群只能有一个项目

这是有意的：只有「群 = 项目」成立，群里说「记一下……」才知道该记到哪儿。
所以在已有项目的群里再说「新建项目」，助理会拦下来：

```
这个群已经是项目 印度纪录片 了，一个群只能对应一个项目。
直接说「记一下……」就会记到它名下。要开新项目请另建一个群。
```

**要开第二个项目就另建一个飞书群，把助理拉进去，在里面说「新建项目：XXX」。**

### 项目名不能重复

即使是不同的群也不行。重名的话，「有哪些项目」列出来的两行长得一模一样，
你分不出哪个是哪个群的：

```
已经有一个叫 印度纪录片 的项目了（在另一个群里），换个名字吧
```

### 打错字了可以改名

```
@助理 项目改名叫印度纪录片二期
@助理 项目名写错了，应该是 8月飞书skill开发
```

```
✅ 项目已改名：印度纪录片 → 印度纪录片二期
已记的日志、任务、复盘都还在原处，链接也没变。
```

改的只是名字 —— 表格、已记的内容、链接一个都不动，项目总表里那一行会跟着刷新。
新名字如果和别的项目撞了，同样会被拦下来（理由同上）。
说的名字和现在一样时回的是「本来就叫这个，没改动」，不会假装改了一次。

## 三、日常记录

在项目群里 @ 助理，说「记一下」「记录一下」「写进日志」：

```
@助理 记一下：今天和导演对了分镜，第三场要重拍
@助理 记录一下，客户说预算追加 20 万，但要提前一周交片
@助理 写进日志：设备明天到，摄影组周三进场
```

助理回：

```
📝 已记到 印度纪录片：今天和导演对了分镜，第三场要重拍
[日志表](https://…)
```

### 三条要知道的规则

**① 原文一个字不改。** 助理只去掉「记一下」「记录一下」这类**指令前缀**，
其余不润色、不摘要、不补主语。日志的价值就在于「当时到底怎么说的」——
复盘是在这些原文之上另外生成的摘要，不会覆盖原始记录。

> 唯一的例外是[「总结群聊」](#四二总结群聊)写进去的那几条：它们是 AI 归纳的，
> 不是谁的原话。所以正文顶着「【群聊摘要 MM-DD】」，网页上还另标一个
> 「AI 归纳（非原话）」——**这张表里哪条是原话必须一眼可辨**，
> 否则它就不能再当证据用了，而那是它唯一的用途。

**② 「记一下」和「提醒我」是两件事。**

| 你说的话 | 助理做什么 |
|---|---|
| 「记一下：客户改需求了」 | 写进项目日志 |
| 「提醒我周五交片」「这个派给张三」 | 建飞书任务 + 进甘特图（见[第三·二节](#三二任务与甘特图)） |

一句话里两样都有时（「记一下客户改需求了，另外提醒我周五交片」），
助理会拆成两步分别办，回帖里两件事都会说。

**③ 同一条消息不会被记两遍。** 飞书的事件是「至少投递一次」——
成功了也可能重推。助理靠 `消息 id + 步序` 去重，重复投递时回的是：

```
这条已经记过了（印度纪录片）。
```

不会悄悄多出一行，也不会谎称新记了一条。

### 单条上限 2000 字

超过会截断并在正文末尾标上「…（原文过长，已截断）」——
不会静默丢字。整段会议记录建议分几条记，或者直接放进云文档再记一条链接。

## 三·二、任务与甘特图

派活也在这个群里说：

```
@助理 指派给 @张三 一个任务，今天开始，3 天后完成，内容是设计项目 logo
@助理 给李四建个任务，下周三前把合同发出来
@助理 提醒我周五交片
```

```
✅ 任务已创建：**设计项目 logo**
负责人：张三
开始：08-10 09:00
截止：08-13 18:00
[在飞书中打开](https://…)
[项目甘特图](https://…?table=tbl…&view=vew…)
```

**一条任务同时落在三个地方**：飞书任务中心（张三的「我负责的」里就有了）、
我们自己的库、以及本群项目的「任务」表 —— 也就是甘特图那张。

### 甘特图是飞书多维表格自带的视图

建项目时「任务」表上就顺手建了一个叫「甘特图」的视图，回帖里那个
「项目甘特图」链接直接指到它。所以「支持甘特图吗」的答案是：支持，
它就是同一张表的另一种画法，你在飞书里还能自己再加视图（看板、分组）。

**没有开始时间的任务在图上只是一个点。** 这一点助理会在建的时候就说，
不会等你打开图才发现少一条横条：

```
（没说开始时间，甘特图上它只是个点；补一句「XXX 那个任务从今天开始」即可。）
```

补法就是下面的改任务。

### 改任务

```
@助理 把季度报告那个任务标记完成
@助理 设计 logo 那个任务改成从明天开始，截止推到下周三
@助理 设计 logo 那个任务状态改成进行中
@助理 刚才那个任务把 @张三 也加进来一起跟
@助理 在季度报告任务下面记一句：数据还差三季度的
```

一句话里说几样就一起改，改完飞书任务和甘特图上那条同时更新。
状态是四个值：**未开始 / 进行中 / 已完成 / 已取消**（说「取消」「搁置了」
都会落到「已取消」，它和「已完成」在图上颜色不同）。

三条要知道的：

- **只能改助理自己帮你建过的任务。** 你在飞书里手动建的它看不见 ——
  不是权限问题，是任务接口只返回调用身份自己创建的东西。
  所以查不到时它说的是「我只能改我自己帮你建的那些」，而不是「没找到」。
- **说不清是哪一个时一律拒绝**，把候选列出来让你重说。连「取时间上最近那个」
  都不做 —— 你说「那个任务」指的是你心里那件事，不一定是最近的一件。
- **可能部分成功。** 飞书把改标题、加协作人、设提醒、写评论分在四个接口上，
  所以回帖会明说哪几样成了、哪几样没成：「上面那几条已经生效了，重下指令请只补这部分」。

### 任务和「记一下」的分工

| 你说的话 | 落在哪 |
|---|---|
| 「记一下：客户说 logo 要改大」 | 「记录」表（原话，不可执行） |
| 「派给 @张三：把 logo 改大，周三前」 | 飞书任务 + 「任务」表 + 甘特图 |

一句话里两样都有（「记一下客户要改 logo，顺便派给张三周三前做完」）会拆成两步分别办。

## 四、复盘

在项目群里：

```
@助理 复盘一下
@助理 总结下本周的情况
@助理 最近 10 天这个项目干了什么
@助理 上周的复盘发一下
```

助理把这段时间的日志取出来交给 AI 归纳，回帖长这样：

```
📋 印度纪录片 · 本周（08-03 至 08-09）
共 12 条记录

这周主要在推进分镜和器材准备，客户侧预算有变化。

关键进展
- 和导演对完全片分镜，第三场确定重拍
- 摄影器材周三进场

需要注意
- 客户追加预算但要求提前一周交片，档期需要重排

[完整复盘记录](https://…?table=tbl…)
```

同一份总结也会写进项目日志表的「复盘」表 —— 群消息会被刷走，而这份总结是
这个功能真正的产出，得有个不会被刷走的位置。

### 时间范围只有这七种

范围是**代码算的**，不是 AI 猜的。你用自然语言说，助理翻译成下面七个词之一：

| 说法 | 范围 | 边界 |
|---|---|---|
| 今天 / 没说时间 | `today` | 当天 00:00 到次日 00:00 |
| 昨天 | `yesterday` | 完整的一天，不含今天 |
| 本周 / 这周 | `this_week` | **周一**到今天 |
| 上周 | `last_week` | 上周一到上周日（完整一周） |
| 本月 / 这个月 | `this_month` | 1 号到今天 |
| 最近 N 天 | `recent_days` | 含今天往前推 N 天（N 限 1–365） |
| 全部 / 从头到现在 | `all` | 不设上下界 |

几个细节：

- **周一为一周的第一天**（国内习惯）。周日说「本周」拿到的是上周一到今天，
  不是周日这一天。
- 时间按**北京时间**（`Asia/Shanghai`）切，不跟随服务器时区 ——
  早会记的那几条一定在「今天」里。
- 回帖里的范围**一定带具体日期**（「本周（08-03 至 08-09）」）。
  不写日期就没法核对到底取了哪几天。
- 说了助理听不懂的范围（「本季度」「上个月」）时，它按**今天**处理，
  并且在回帖里如实写「今天」—— 不会悄悄给你一份三个月的汇总。

### 这段时间没人记录时

助理**不会**花 AI 额度去总结一份空数据，也不会说「本周没有明显进展」
（那是两件完全不同的事）：

```
印度纪录片 在今天没有任何记录，所以没什么可复盘的。
这个项目一共有 37 条记录，换个时间范围试试（比如「上周的复盘」「全部复盘」）。
```

项目一条记录都没有时，它会引导你先去记，而不是让你换范围。

### 两个上限

- 单次复盘最多喂 **300 条**记录。超了保留**最近**的 300 条，
  并在总结开头写明「更早的 N 条未纳入」。
- 群里回帖最多 **1500 字**。超了截断并指向复盘表，
  完整版永远在表里（存表用的是不截断的那份）。

### 复盘时模型看得到项目现状

每条指令（不只是复盘）都会带上一小段「本群这个项目现在什么状况」：项目名、
最近几条记录、没做完的任务。这是为了让「那个 logo 的活推到周五」「这周做了什么」
这类话有依据 —— 没有它，「那个 logo 的活」对模型只是一串没有指代的字。

**它只用来听懂话，不替你做决定。** 里面不含任何 id，任务标题列出来也不会被
用来替你补全「哪个任务」—— 说不清是哪一个时照样会把候选列给你挑。
条数有上限（最近 5 条记录 / 8 个未完成任务），列不全的部分会在那段里明说，
免得模型把「列表里没有」当成「不存在」。

## 四·二、总结群聊

日志得有人记，而项目群里真正的信息往往是聊出来的、没人回头补一句「记一下」。
所以有这个功能：**助理去读本群的聊天原话，自己挑出该记的几条写进日志。**

```
@助理 总结一下今天群里聊了什么
@助理 把今天的群聊整理进日志
@助理 整理下昨天群里的消息
@助理 最近两天群里的内容总结一下
```

```
📋 今天（08-10）的群聊我读了 46 条，挑出 3 条记进了 印度纪录片 的日志：
1. 李四说客户要求把 logo 改大，下周一之前给新版
2. 王五说摄影器材周三上午到场，需要有人在现场签收
3. 张三说预算追加的 20 万已经批下来了

⚠️ 这几条是我根据群聊**归纳**的，不是谁的原话（日志表里带「群聊摘要」前缀）。有归纳错的地方说一句，我按你说的原话再记一条。
（跳过了 5 条图片/文件等非文字消息、8 条「收到」「好的」这类。）
[日志表](https://…)
```

### 这和复盘是两件事

| | 读什么 | 产出 |
|---|---|---|
| **总结群聊**（`digest_chat`） | 群里的**聊天原话**（没人记过的） | 往日志里**新增几条记录** |
| **复盘**（`review_diary`） | **已经记在日志里**的内容 | 一段总结，发群里 + 存进「复盘」表 |

只说「复盘一下」「这周干了什么」时是复盘；明确提到**群里的聊天**时才是这个。

### 一次最多读 3 天

范围只有 `今天 / 昨天 / 最近 N 天（N ≤ 3）`，比复盘的七种窄得多。理由是
一个活跃群一个月上万条消息，而喂给模型的上限是 200 条 —— 允许「本月」的后果
不是报错，是产出一份写着「本月」、实际只覆盖最后半天的摘要，**而它会永久留在日志表里**。

所以超范围是**明说做不到**，不静默按「今天」办：

```
群聊记录我一次最多读 3 天（群里消息量太大，读不完的部分会被丢掉，而一份只覆盖了一小段的「本月总结」比没有更糟）。
试试「总结一下今天群里聊了什么」；要看整个项目的情况请说「复盘一下本月」——那个读的是日志，没有这个限制。
```

### 哪些消息不算

助理在读的时候就把这些滤掉，并**分类数出来告诉你**：

| 滤掉的 | 为什么 |
|---|---|
| 图片、文件、语音等非文字消息 | 读不了。**这一类最值得看数字** —— 那天的正事全发在图里时，你才知道要自己补一句 |
| 已撤回的 | 飞书照样返回它们（正文是一句英文提示） |
| @ 助理的指令消息 | 那是你在跟助理说话，不是群里的事 |
| 助理和其他机器人的消息 | 不然摘要会开始总结助理说过的话 |
| 「好的」「收到」「辛苦了」这类 | 不携带信息，只挤占额度 |

一条文字消息都没读到时不花 AI 额度，回的是「这段时间群里没读到可以总结的文字消息」
加上那份跳过计数 —— 「真的没人说话」和「说了但全是图片」是两件不同的事。

### 几条要知道的规则

**① 挑不出东西是正常结果，不是失败。** 群里聊了一天闲天很常见，模型被明确要求
宁可返回空也不要编：

```
读了 46 条今天的群消息，没挑出需要记进日志的内容（决定、客户要求、进度、问题、钱和时间这类）。
有该记的事直接说「记一下……」，我原样记下来。
```

**② 每条都写清是谁说的。** 「有人提到预算要追加」和「李四说预算要追加」在项目里
是两回事。记录人记的是**下指令的你**（这几条是你让助理生成的，出问题找你核对）。

**③ 归纳的内容永久带标记。** 日志正文顶着「【群聊摘要 MM-DD】」，
网页上另标「AI 归纳（非原话）」，项目卡片上的条数也把它单独括出来
（「120 条记录（含 18 条群聊摘要）」）。归纳错了说一句，助理按你说的原话再记一条 ——
**旧的那条不会被删**（日志只追加）。

**④ 同一段时间可以总结第二次。** 上午总结过、下午又聊了两小时是常态，拦掉等于
让下午的事永远进不了日志。但会说清是第几份：

```
（这已经是今天（08-10）的第 2 份摘要，和之前那份可能有重复。）
```

**⑤ 读满 500 条会截断，保留的是最近的那批**，并在回帖里明说更早的没读进来。

### 单次上限

- 一次最多读 **500 条**消息，其中最多 **200 条**参与归纳（取最近的）。
- 最多抽 **8 条**，每条最长 200 字。

## 五、生成的几张表长什么样

### 先说怎么找到它们

⚠️ **这些多维表格不在你的云文档空间里，也搜不到 —— 链接是唯一入口。**

原因是它们由机器人身份创建（建表时没有指定归属文件夹），而且链接分享是主动关掉的
（见第六节）。所以：

**链接被消息刷走了，就 @ 助理说一句「有哪些项目」**：

```
@助理 有哪些项目
```

```
📊 [项目总表](https://…?table=tbl…)

共 3 个项目：
· 印度纪录片（本群） — 37 条 [日志表](…)
· 春节品牌片 — 12 条 [日志表](…)
· 客户A改版 — 0 条 [日志表](…)

（项目总表只有建项目的人能打开；各项目的日志表对应群里的人都能看。）
```

也可以说「项目列表」「项目总表的链接发一下」「本群的日志表在哪」。
这个指令**不花归纳的额度**（纯读库，不调 AI 去总结），而且它列的是**全公司**的项目，
在哪个项目群里问都一样。

**不在飞书里的时候**，登录平台打开 `/feishu` >「项目日记」标签，同一份清单在那儿：
项目名、群名、记录条数（**其中几条是群聊摘要单独括出来**）、任务数和在办数、
复盘次数、最后一条的时间，以及日志表和复盘表的链接。
点进某个项目还能直接在网页上翻日志正文和历史复盘（复盘那份是**完整版**，
群里发的那条被截到 1500 字），AI 归纳的那些记录带一个「AI 归纳（非原话）」的标。
「未同步」也在这一页上，而且**记录和任务是分开数的**（两条同步路径）。
这一页是**只读**的 —— 理由见第九节。

> 建项目那一次的回帖里，日志表和项目总表的链接都会给出来。
> 「有哪些项目」和网页上那一页都是为了**事后找回** ——
> 群消息会被刷走，而这两张表在飞书里没有别的入口。

### 项目总表（每家公司一份，第一次建项目时自动创建）

| 列 | 类型 | 说明 |
|---|---|---|
| 项目名称 | 文本 | |
| 日志表 | 超链接 | 点开就是那个项目的日志表 |
| 关联群聊 | 群 | **点开能直接跳进那个群** |
| 记录数 | 数字 | 每次记录后自动刷新 |
| 创建人 | 人员 | |
| 创建时间 | 日期 | |

这张表只授权给**建项目的那个人**（可编辑），不授权给任何群 ——
它是全公司所有项目的清单，而项目群只该看到自己那个项目。

### 项目日志表 > 「记录」

| 列 | 类型 |
|---|---|
| 记录 | 文本（原文） |
| 时间 | 日期 |
| 记录人 | 人员 |

AI 从群聊归纳的那几条也在这张表里，正文顶着「【群聊摘要 MM-DD】」——
**没有单独一列**来标它。理由是 068 之前建的项目这张表只有上面三列，
而往多维表格写一个表里不存在的字段名会让**整批**同步失败：
为了一个标记把老项目的日志全部推不上去，是划不来的。

### 项目日志表 > 「任务」（带一个「甘特图」视图）

| 列 | 类型 | 说明 |
|---|---|---|
| 任务名称 | 文本 | |
| 负责人 | 人员 | |
| 开始时间 | 日期 | 缺它的话这条在甘特图上只是个点 |
| 结束时间 | 日期 | |
| 状态 | 单选 | 未开始 / 进行中 / 已完成 / 已取消 |
| 内容 | 文本 | |
| 派活人 | 人员 | |
| 飞书任务 | 超链接 | 点开就是任务中心里那条 |

甘特图用哪两列画横条是飞书那侧按字段类型自己认的（表里只有这一对日期列）。
甘特视图建不出来时只是少一张图 —— 数据全在，回帖会说一句，
你也可以在飞书里手动加一个视图。

### 项目日志表 > 「复盘」

| 列 | 类型 |
|---|---|
| 时间范围 | 文本（如「本周（08-03 至 08-09）」） |
| 生成时间 | 日期 |
| 记录数 | 数字 |
| 发起人 | 人员 |
| 总结 | 文本（完整版，不截断） |

**你可以自己往这些表里加列**（比如「跟进人」「是否已同步客户」）。
同步是**只追加**的 —— 助理只往里加行，从不回读、从不覆盖，
所以你加的列不会被冲掉。**但也别改上面这些列的名字**：
同步是按字段名写的，改了名那一批就整批推不上去（回帖会告诉你没同步，
但表里从此一直缺行）。

## 六、权限：为什么表对群里是只读的

建项目时助理做了两件权限动作：

1. **关掉链接分享。** 不关就跟随飞书租户的默认值，而默认往往是
   「组织内获得链接的人可阅读」+「可转发到组织外」。日志表链接是**发在群里**的，
   于是全公司任何拿到链接的人都能看这个项目的全部日志。
2. **把表授权给本群，只给「可阅读」。**

第 2 条是刻意的，理由值得说清楚：

> 同步是只追加的 —— 记录推上去之后就不会再推第二遍。所以**群里任何人删掉一行，
> 那行就再也不会回来**（我们库里还有，但表和库从此不一致，而人看的是表）。
> 给整群编辑权限，等于让任何成员都能不可逆地删掉项目日志。

要记日志就在群里 @ 助理 —— 那条路径每条都有记录人、有时间、可追溯。

「任务」表是唯一会被**改**的一张（改任务时按行号更新那一行，否则甘特图上
一条任务会有好几根横条）。所以在表里手动删掉一行任务之后，再改这条任务时
那次更新会失败，回帖里会说「没同步」—— 同样是删不回来。

---

### 改任务表的列名 = 那张表从此不再更新

同步是按**字段名**写的（「任务名称」「开始时间」…）。改了名字之后飞书会拒掉
整批写入，表现是回帖里一直说「有 N 条没同步」而表里再也不长新行。
加列没问题，改名和删列不行。

这两步都会失败（权限没发版是最常见的原因），失败时助理会在回帖里**明确说出来**，
而不是假装成功：

- 「表已建好，但把它开放给本群失败了…群里点链接会显示无权限，请在飞书里手动分享给本群」
- 「⚠️ 这张表的链接分享没关成功，组织内拿到链接的人都能看，请在飞书里手动收紧」

看到第二条要去手动处理一下 —— 那是个信息泄露面，不是观感问题。

## 七、AI 额度怎么算

助理每收到一条指令，都要调一次大模型来「听懂这句话」。所以：

| 操作 | AI 调用次数 |
|---|---|
| 新建项目 / 改项目名 | 1（听懂） |
| 记一条 | 1（听懂） |
| 派任务 / 改任务 | 1（听懂） |
| 列出所有项目 | 1（听懂；纯读库，不归纳） |
| **复盘** | **2**（听懂 + 归纳） |
| 复盘但范围内没记录 | 1（不会为空数据花第二次） |
| **总结群聊** | **2**（听懂 + 归纳） |
| 总结群聊但一条文字消息都没读到 | 1（同上，不为空数据花第二次） |
| 总结群聊但范围超过 3 天 | 1（当场拒绝，连读消息的接口都不调） |

额度记在**绑定这个飞书应用的平台账号**上 —— 在飞书里说话的人不需要有平台账号。
如果给「飞书助理」单独配了应用额度，记得把复盘和总结群聊的双倍消耗算进去。

## 八、常见问题

**Q：在群里 @ 了助理，一点反应都没有。**
先看 `/feishu` 应用卡片上有没有「某个群 @ 过 N 次，都被白名单拦下了」——
被白名单拦下是**静默丢弃**的（在陌生群里回话等于向任意群暴露自己），
这是「没反应」最常见的原因，那里有一键放行。排除它之后再看连接状态和指令日志。

**Q：助理说「这个群还没有对应的项目」。**
先在这个群里说一句「新建项目：XXX」。项目是按群绑的，换个群就是另一个项目。

**Q：回帖说「已记到系统里，但有 N 条还没同步到多维表格」。**
记录**已经安全落库了**，不会丢。同步失败通常是限流或权限。
**不要重说一遍**（那会在表里留下两条内容相同、时间不同的记录）——
下次在这个群里记录时，欠的那几条会连着新的一起补推。

> 注意：补推是**跟着下一次记录**发生的，没有后台定时任务。
> 如果这个项目之后一直没有新记录，那几条会一直停在「未同步」——
> 库里查得到，表里看不到。随便再记一条就会补上。

**Q：表格链接被群消息刷走了，去哪找？在云文档里搜不到。**
搜不到是对的 —— 表由机器人身份创建，不在任何人的云文档空间里，链接分享也是关掉的。
**@ 助理说一句「有哪些项目」**，它会把项目总表和每个项目日志表的链接一并列出来
（列的是全公司的，在哪个项目群里问都一样）。
或者登录平台打开 `/feishu` >「项目日记」，那一页列着所有项目和它们的表格链接。

**Q：群里点日志表链接，显示「无权限访问」。**
说明授权给群那一步失败了（回帖里应该有提示）。去飞书里手动把这张表分享给这个群
（只读就够），或者检查 `drive:drive` 权限有没有**发布版本**。

**Q：复盘说「没有任何记录」，但我记得记过。**
先看范围对不对 —— 回帖里写着具体日期，对一下。周日说「本周」是周一到今天；
说「昨天」不含今天。不确定就说「全部复盘」。

**Q：复盘回帖说「这次归纳没成功…下面是原始记录，不是总结」。**
模型没返回可用结果（偶发）。助理退化成按时间列出原文，
并且**如实说明这不是总结** —— 记录是真的，只有归纳这一步歪了。再说一次复盘通常就好。

**Q：我在表里手动加了一行，助理复盘时没算进去。**
表是**镜像**，数据源在我们库里。手动加的行只在表里，复盘取的是库里的记录。
（这也是为什么群里是只读的。）

**Q：项目名打错了。**
说一句「项目改名叫 XXX」就行（见[第二节](#打错字了可以改名)）。
**删项目**目前没有指令，见下一节。

**Q：说「总结一下群里聊了什么」，回的是缺权限。**
`im:message.group_msg` 是**可选权限**，不在接入指引的必需清单里
（那一档飞书审得最严，而这个功能不是所有人都用）。回帖里写着缺哪一项、
附一键跳转，开完**记得发布新版本**。见[第一节](#还有一组是可选的读群聊记录)。

**Q：群聊摘要写错了 / 归纳得不准。**
说一句「记一下：<正确的原话>」补一条原话进去。**错的那条不会被删**
（日志只追加），但它带着「【群聊摘要】」前缀，以后翻表的人分得出哪条是原话。

**Q：「总结本月群聊」被拒绝了。**
一次最多读 3 天 —— 群里消息量太大，读不完的部分会被丢掉，而一份只覆盖了
一小段的「本月总结」比没有更糟（而且它会永久留在日志表里）。
要看整段时间的情况用**复盘**，那个读的是日志，没有这个限制。

**Q：甘特图上有一条任务只是一个点，没有横条。**
那条任务没有开始时间。说一句「XXX 那个任务改成从今天开始」补上。

**Q：任务在甘特图上看不到 / 状态是旧的。**
先看回帖里有没有「⚠️ 任务已在飞书建好，但没能记进项目的任务表」这类话 ——
任务和记录是**两条独立的同步路径**，各自有自己的「未同步」计数
（`/feishu` >「项目日记」和后台都分开显示）。任务的补推跟着**下一次派活/改任务**发生。

**Q：解绑飞书应用之后呢？**
库里的项目、记录、复盘会被清掉（否则重新绑定同一个应用后，那些项目会指向
上一次建的表格，而新的应用身份对那些表没有任何权限 —— 表现是「记一下」永远同步失败）。
**飞书里的多维表格本身不删**（那是你的数据，删了没有回收站），
但从此不再由助理维护。要留着历史数据的话，解绑前先把表格另存一份。

## 九、目前做不到的事

诚实列一下，省得试半天：

- **删项目 / 归档项目**：没有对应指令（**改名有**，见第二节）。
  需要的话得手动改库（`feishu_diary_projects`）。
- **删一条记录 / 改一条记录**：没有。日志按设计是只追加的。
  AI 归纳错的那条也删不掉，只能补一条原话（那条带着「群聊摘要」前缀，分得出来）。
- **删一条任务**：没有。可以把状态改成「已取消」——
  它在甘特图上和「已完成」颜色不同，等于软删除。
- **列任务 / 查「我有哪些活」**：做不到。任务接口只返回**调用身份自己创建的**东西，
  要读别人的得走用户 OAuth。所以助理只能改它自己帮你建过的那些，
  「这个项目派了哪些活」要去看「任务」表或甘特图。
- **一个群多个项目**：不支持，这是这个功能的核心约束（见第二节）。
- **私聊里用**：整个助理都只在群聊里工作 —— 私聊 @ 它只会收到一句「请到群里 @ 我」
  （项目要绑群，而私聊没有可绑的群）。
- **跨项目的汇总复盘**（「所有项目这周怎么样」）：一次只复盘一个项目。
- **「整个项目的总结」「阶段性总结」这种说法**：没有专门的范围词。
  能表达的是那七个时间范围 —— 「全部复盘」就是整个项目的总结，
  阶段性的用「上周」「本月」「最近 30 天」。想按里程碑分段（「第一阶段」）做不到，
  因为库里没有"阶段"这个概念。
- **总结群聊超过 3 天**：读不完，会被明确拒绝（见第四·二节）。
- **总结群聊读的是「没有 @ 我的消息」**，所以要那个可选权限；
  图片、文件、语音里的内容一律读不到（会数出来告诉你）。
- **把复盘写成云文档**：v1 只发到群里 + 存进「复盘」表，不生成 docx。
- **给复盘或群聊摘要设定时任务**（每天下班自动总结一次、每周五自动复盘）：
  **没有**，得有人去群里说一句。整个模块没有任何后台定时任务，
  连表格的补推都是跟着下一次记录发生的。
- **在网页上改东西**：`/feishu` >「项目日记」能**看**（项目清单、两个表格的链接、
  日志正文、历史复盘的完整版），但**只能看**。
  理由是同步只追加：网页上删掉一条，多维表格里那一行删不掉（推上去就置状态位，
  永不重推），于是库和表从此不一致，而用户看的是表。
  要改、要记，都在群里 @ 助理 —— 那条路径每一步都有记录人、时间和原始消息 id。
- **多人同时在同一个群建项目**：会有一个成功，另一个收到「这个群已经是项目 X 了」——
  这是对的，不会建出两套表。

### 代码位置

```

├── diary/
│   ├── store.ts        纯 SQL，不碰飞书接口
│   ├── bitable.ts      只调飞书接口，不写 SQL
│   ├── range.ts        七个枚举值 → 时间窗口（窗口在代码里算，不让模型给）
│   ├── taskStatus.ts   四个状态枚举 ↔ 中文标签（同一条规则：格式不让模型给）
│   ├── context.ts      「本群项目现状」那段 prompt 上下文（不含任何 id）
│   ├── summarize.ts    复盘：调 LLM（fast 档 + json_object）→ 代码渲染 markdown
│   ├── chatHistory.ts  读群消息（唯一会抛的一层；倒着翻页，正序返回）
│   ├── digest.ts       群聊摘要：调 LLM → 几条能进日志的短句
│   └── diary.test.ts   142 个用例
├── actions/diary.ts      五个动作：编排 + 面向用户的话术
├── actions/chatDigest.ts digest_chat：串起 chatHistory + digest + store + bitable
├── actions/createTask.ts 建任务（先飞书、后落库、再推甘特图）
└── actions/updateTask.ts 改任务（先查库、再回落执行日志）
```

六个动作：`create_diary_project` / `rename_diary_project` / `list_diary_projects` /
`add_diary_record` / `review_diary` / `digest_chat`，加上任务那两个
（`create_task` / `update_task` —— 它们不在 `diary.ts` 里，但项目任务表是它们写的）。

其中 `list_diary_projects` 是纯读库的 —— 不碰飞书接口、不调 LLM 归纳，
存在的理由只有一个：**那些多维表格没有别的入口**（见第五节），
它和建项目回帖里的那两个链接是同一件事的两半（建完给一次、事后能找回）。

`digest_chat` 是这一组里唯一**主动读用户聊天**、也是唯一**把 LLM 写的字落进日志表**
的动作，所以它有三条别处没有的约束（都写在 `actions/chatDigest.ts` 的文件头）：
每一行标 `origin='chat_digest'` + 正文加前缀；范围窄到三个值并**明确拒绝**超出的
（不静默降级）；读不到/抽不出都是正常结果，但要分清是哪一种。
它声明的 `im:message.group_msg` 走 `optionalScopeGroups()`，**不进** `allRequiredScopes()`
——理由和当年删掉五个日程动作的第二条一样，见 `actions/index.ts` 的注释。

网页侧是三个**只读**路由（`api/feishuAssistant.ts` 的「项目日记」一节）：
项目清单 + 总表链接、某项目的日志（带 `origin`）、某项目的复盘。前端在
`/feishu` >「项目日记」，后台 `/admin/feishu` 只借第一个路由显示计数。
为什么只读、`:projectId` 为什么必须连 `app_id` 一起校验、`unsynced_count` 为什么
必须露出来，见 [FEISHU_ASSISTANT.md](./FEISHU_ASSISTANT.md) 第九节
「`feishu_diary_*`：网页侧三个路由，全部只读」。

统计字段（`record_count` / `digest_count` / `task_count` / `open_task_count` /
`unsynced_count` / `unsynced_task_count` / `summary_count`）由 `store.projectStats()`
一次算完，缺省值取 `store.emptyStats()` —— **接口层不要另抄一份字面量**：
抄的那份不会跟着这里加字段，而漏掉的键在前端读成 `undefined`、渲染成空白，
和「有数据但是 0」看起来完全一样。

分层的理由：飞书那侧挂掉时只降级成一句 warning，不会丢记录。
所以 `bitable.ts` 里**只有 `createProjectBitable` 会抛错**（base 都没建出来的话
项目等于不存在，调用方要回滚占位行），其余每一步失败都返回 warning 让回帖带上。
`chatHistory.ts` 是这条规则的**唯一例外**，而且是刻意的：读不到群消息意味着
`digest_chat` 一件事都做不了，降级成「今天没什么可记的」是在撒谎，而那句谎话
看起来完全正常。

### 数据表（migration 066 / 068 / 069）

| 表 | 键 | 说明 |
|---|---|---|
| `feishu_diary_indexes` | `app_id`（主键） | 每家公司一份项目总表 |
| `feishu_diary_projects` | `(app_id, chat_id)` 唯一、`(app_id, name)` 唯一 | 两个唯一索引对应两种冲突话术。068 加了 `task_table_id` / `task_view_id` |
| `feishu_diary_records` | `(app_id, message_id, step_index)` 唯一 | 这个唯一键是重放幂等的唯一保证。069 加了 `origin` / `digest_range` |
| `feishu_diary_summaries` | — | `bitable_synced_at` 是同步状态位 |
| `feishu_project_tasks`（068） | `(app_id, message_id, step_index)` **部分**唯一索引 | `message_id` 可能是空串（非指令来源），而 SQLite 里 `''` 是正常值会互撞，所以是带 `WHERE` 的部分索引而不是表级 UNIQUE。`project_id` **可空**（没绑项目的群里派活也要落库） |

069 的两列各自对应一个"看起来成功了"的坏结果：

- **`origin`**（`'manual'` / `'chat_digest'`）—— 066 定的规矩是**记录原文不改写**，
  而群聊摘要是 LLM 写的散文。混在同一列里不加标记的后果不是"数据不整齐"，
  是这张表**整体失去可信度**：半年后没人分得清「客户要求 logo 改大」是谁说的、
  还是模型从「logo 是不是有点小」里推出来的 —— 而这张表存在的唯一理由就是
  「当时到底怎么说的」。多维表格那侧**不加列**（老项目的表没有它，写未知字段名会让
  整批同步失败，连正常记录一起卡住），改为在正文前面顶一行「【群聊摘要 08-10】」。
- **`digest_range`**（`today:2026-08-10` 这种，空串 = 不是摘要）—— 同一段时间可以
  总结多次（不拦，否则"下午的事"永远进不来），但要能数出「这是第几版」并说出来，
  否则日志里出现三条内容七成重合的摘要，看的人以为群里真讨论了三轮。
  **`store.countDigests` 数的是 `COUNT(DISTINCT message_id)`，不是 `COUNT(*)`**：
  一次总结写好几行，用 `COUNT(*)` 的话第二次会报成「第 6 份」。

068 的任务表存在的理由（为什么飞书任务不够）三条，都写在迁移文件头：
`task.list` 只返回调用身份自己创建的东西、飞书任务没有「开始时间」（甘特图要两端）、
任务改名后历史名字在飞书那侧就不存在了而用户永远用新名字称呼它。

**隔离键是 `app_id`**（飞书那个 `cli_xxx`），和名册（057）、会话（058）一样：
一个自建应用 = 一家公司的租户。没有外键级联，解绑时在 `appStore.deleteApp` 里手动清。

> ⚠️ `ctx.appId` 是飞书的 `cli_xxx`，**不是 `feishu_apps` 表的行 id**。
> 查应用要用 `getAppByAppId`，用 `getApp` 会一律查不到 —— 而且不报错
> （复盘的额度会记到空账号上）。

**已知的一个小缺口**（实测确认，目前走不到）：`(app_id, name)` 的唯一索引是
**大小写敏感**的（SQLite 默认），而 `findProjectByName` 是大小写**不**敏感的。
所以「Brand Film」和「brand film」能同时存在，此时按名字找项目命中的是
`listProjects` 里排在前面的那个 —— 而它按 `created_at DESC` 排，
同毫秒创建时顺序不确定。**这是本模块唯一一处会"猜"的地方**，和「绝不模糊匹配」
的原则相悖。

现在撞不到它，因为按名字找项目只出现在 `resolveProject` 的非群聊分支，而私聊在
dispatcher 就被挡掉了（群里一律按 `chat_id` 定项目，不看模型填的 `project` 参数）。
**哪天再开一条按项目名进来的路（跨项目复盘、网页端下指令），这个缺口就活了。**
堵法：在 `claimProject` 插入前查一次 `findProjectByName`，命中就抛
`ProjectConflictError('name', …)`。

### 四条贯穿本模块的规则

1. **模型不输出它能悄悄搞错的格式。** 参数里没有 `chat_id` / `app_token` /
   `record_id` / `guid`；时间范围是七个枚举值，窗口由 `range.ts` 算；
   任务状态是四个枚举值，中文标签由 `taskStatus.ts` 给；负责人是**姓名**，
   open_id 由 `people.ts` 从 mentions 或名册里查；markdown 由代码渲染，
   模型只填 JSON 内容。这和 open_id、RRULE 是同一条规则。
2. **库先落地，表格后同步。** 表格是镜像。写表失败只回一句「下次补推」，
   不让整条指令失败 —— 那会让用户再说一遍，最后表里两条。
   （建任务是唯一反过来的：先飞书、后落库 —— 见 `createTask.ts` 的文件头，
   反了会留下「甘特图上有、负责人任务中心里没有」的行。）
3. **任何被丢掉的东西都要说出来。** 截断、未同步、链接分享没关上、
   归纳失败退化成原文清单、群聊里跳过的图片和撤回、超出 3 天的范围被拒 ——
   静默降级读起来就是成功。
4. **LLM 写的字必须能一眼分出来。** 只有 `digest_chat` 会把模型写的内容
   放进日志表，所以它落库时标 `origin='chat_digest'`、正文顶前缀、
   回帖里明说「这是我归纳的，不是谁的原话」、网页上另标一个标签、
   卡片上的条数把它单独括出来。四处都是同一件事的不同位置，少哪一处都会有人
   在那个位置上把它当成原话。

### 加东西时要一起改的地方

动作注册表（`actions/index.ts`）会自动生成意图解析的 prompt、「接入指引」页的
权限清单（必需的走 `allRequiredScopes()`，可选的走 `optionalScopeGroups()`），
以及没听懂时那句「我目前会…」的能力清单（`ActionDef.hint` → `capabilityHints()`）。
但下面这几处是**手写的散文**，改了能力不改它们就会静默过期：

- `dispatcher.ts` 的 `fallbackReply()` 里那两句限制（清单本身是生成的，限制是手写的）
- `intent.ts` 的 `diaryHint()`（群无项目 / 群有项目两个分支，
  以及复盘 vs 总结群聊的那句分界）
- `client/src/views/feishu/FeishuHome.vue` 的 `<ul class="caveats">`
- 本文档

六个日记动作在 `ACTIONS` 数组里**必须挨在一起**，而且整块排在任务动作
（`create_task` / `update_task`）**之前**。模型是顺着读动作列表的，先撞上一个
说得通的就选了：日记块原先排在末尾（第 9-12 位）而 `create_task` 在第 3 位，
于是「添加新项目，XX 纪录片」一路撞到 `create_task` 上就停了 ——
回帖「✅ 任务已创建」，看着像成功，用户要的那张日志表根本没建。
两条都有测试守着（`diary.test.ts`「日记动作紧挨着，且整块排在任务动作之前」）。

块**内部**的顺序同样是功能，两处：

- `rename_diary_project` 紧跟 `create_diary_project`（建和它的改相邻）。
  一个群只能有一个项目，所以「项目改名叫 X」和「新建项目 X」是同一件事的两种说法；
  隔远了的表现是改名被选成建项目，回一句「这个群已经是项目 Y 了」——
  而用户要的正是把 Y 改掉。
- `digest_chat` 紧跟 `review_diary`，且**复盘在前**。两者都是"总结"，串了之后
  用户拿到的东西是反的：他要助理去读群聊，收到的是一份基于日志的总结，
  而群里的事本来就没人手动记过，于是那份总结是空的。复盘在前是因为
  「总结一下」这句话绝大多数时候要的是复盘。

顺序只改变「先看到谁」，不说明「为什么不是那个」—— 后者是 `intent.ts` 的
`PROJECT_VS_TASK_RULE` 加上写在 `create_task` / `update_task` **自己描述里**的排除句
（写在被误选的那个动作上，因为模型读到它时 `create_diary_project` 的文字已经在很上面了）；
复盘/总结群聊那一对同理，两个动作**各自的** description 里都写了对方是什么。
缺任何一半都还会串味。

### 测试

```bash
source ~/.nvm/nvm.sh && nvm use v21.7.3
npx vitest run src/services/feishuAssistant
```

`diary/diary.test.ts` 的基准时间刻意选了 **2026-08-09（周日）**：
`this_week` 的 `(weekday + 6) % 7` 是最容易写错的一处，
少了 `+6` 周日复盘「本周」只会拿到周日一天，而那天通常一条记录都没有 ——
表现成「这周什么都没干」，不报错。

`digest_chat` 那一组用 `vi.useFakeTimers({ toFake: ['Date'] })`（只假造 `Date`，
不动定时器 —— 动了的话 SDK 里的重试会挂住）。它专门守着几件从现象上看不出来的事：
喂给飞书的 `start_time`/`end_time` 是**秒**而返回的 `create_time` 是**毫秒**、
翻页倒着翻而喂给模型的行是正序、读满上限时保留的是**最近**那批、
`step_index` 用 `stepIndex * 100 + i` 错开（少了它飞书重投时第 2..N 条会撞上第 1 条的键，
表里只剩一条而回帖说「已记 5 条」）、以及范围超 3 天时**一次接口都不调**。

注册表约束那一组（`describe('注册表约束')`）守的是上面「加东西时要一起改的地方」
里那几条排序和权限规则 —— 它们全都是"不报错但结果是反的"那一类，
只有断言才拦得住。
